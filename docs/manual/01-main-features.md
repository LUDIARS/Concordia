# 主要機能

Concordia の機能は多岐にわたりますが、人間の目線では次の 9 つの塊に整理できます。それぞれについて「何ができるか」「どこから使うか」「どのサービスと連携するか」「実装状況」を示します。

実装状況の欄は、リポジトリの spec の status と `src/` 配下の実在コードを突き合わせて記載しています。spec に「planned」とあるものは、たとえ設計が承認済みでも「設計のみ」と書いています。

## 1. セッション協調 — 誰が・どこで・何をしているかの共有

Concordia の中核です。エージェントのセッションが始まると自動で登録され、リポジトリ・ホスト・ブランチ・現在のタスクが記録されます。同じリポジトリを触っている他のセッションがいれば、開始時点で双方に知らされます。同じブランチまで重なっていたら、worktree を分けて作業するよう提案が注入されます。強制ロックは一切なく、あくまで「気付かせて、自律的に避けさせる」方式です。

セッションが黙って落ちた場合も拾います。ハートビートが 30 分途絶えるとロスト扱いになり、Concordia がそのセッションの transcript ファイルを読んで最後の作業内容を復元します。次に同じ場所でセッションを立ち上げると「前にここで止まった作業がありますが、引き継ぎますか」と提示されます。

セッション終了時には、蓄積されたイベントから作業レポートが自動生成されます。LLM による要約と、機械的な集計 (編集ファイル一覧・TODO 完遂率など) の両方が残ります。

- **入口**: すべて自動 (フック経由)。閲覧は WebUI の Monitor / Reports、または MCP ツール。
- **連携**: Lictor (transcript 中継・ブランチ報告)。
- **実装状況**: 実装済み。

## 2. Discord / Slack 連携 — チャットがそのまま職場になる

人間が Concordia に触る主要な入口は Discord です。Discord には 3 つのフォーラムがあり、**Session フォーラムに新規投稿するとそれだけで AI セッションが起動します** (spawn-by-post)。投稿タイトルにプロジェクトコード (例 `[Cc]`) を書けば作業ディレクトリも決まり、投稿本文が最初の指示になります。以後そのスレッドがセッションとの会話窓で、返信すれば追加指示として注入され、セッションの回答も同じスレッドに返ってきます。どのエージェントで起動するかは投稿の内容から決まります。フォーラム起動用に登録されたテンプレート群を候補に、投稿のタイトルと本文を読んだ分類器が 1 つを選ぶ仕組みです (`src/discord/forum-delegation-selector.ts`)。

メッセージへのリアクション (絵文字) も指示になります。あらかじめ登録したワークフロー (PR をマージする、タスクとして委託する、など) を絵文字 1 つで発火できます。ほかに `/spawn` `/end-session` `/confirm` などのスラッシュコマンド、Excubitor 経由でサービスを再起動する `/ex-run` `/ex-reboot` もあります。Slack にも同等の Hub + セッション別チャンネル構成があります。

- **入口**: Discord (フォーラム / リアクション / スラッシュコマンド)、Slack。
- **連携**: Lictor (会話の双方向中継)、Excubitor (再起動コマンド)。
- **実装状況**: 実装済み (フォーラム移行・Slack platform とも)。細部の後続 spec (セッションチャンネル直接 inject、コントロール UI 拡張、ぼやきチャンネル) は設計のみ。
- **注意**: フォーラム移行 spec 自体には status フィールドが無く「approved」表記ですが、`src/discord/forum-spawn.ts` ほか実装コードが実在するため実装済みと判断しています。

## 3. 委託 (Delegation) — 別のエージェントに仕事を投げる

「タスクテンプレート」を呼び出し名で発火して、別の AI エージェントを起動する仕組みです。Claude が設計書を書き、実装だけ Codex に投げる、といった分業の土台になります。テンプレートにはプロンプト雛形・対象プロバイダ (claude / codex / codex-sdk / gemini / ローカル LLM)・モデル・作業ディレクトリが登録されており、変数を埋めるだけで子セッションが spawn されます。実行履歴 (run) はすべて記録され、TaskWorkflow フォーラムでは 1 run = 1 スレッドとしてログが追えます。

テンプレートは雇用形態で 3 分類されています。spawn される汎用ワーカーが「従業員」、呼び出し専用の特化タスクが「フリーランサー」、cron や朝タスクで時限起動するものが「パートタイマー」です。モデル指定を auto にすると、要求品質に応じたモデル選択 (Famulus 連携) も働きます。

- **入口**: MCP ツール (`delegation_invoke`)、REST API、WebUI の Delegation ページ、Discord (フォーラム投稿・リアクション)。
- **連携**: Claude Code / Codex CLI / Gemini CLI / Satelles (codex-sdk レーン) / Famulus (モデル自動選択)。
- **実装状況**: 実装済み。子会社 (拠点側での委託実行) は設計のみ。

## 4. タスクワークフロー — 分解から自走までの一本道

実装タスクを「md ファイルへの分解 → 委託実装 → 安定ブランチでのテスト → 残作業チェック → 次タスクへ自走」という一本のパイプラインに載せる構想です。タスクの正本は各リポジトリの `spec/tasks/*.md` に置き、Concordia が走査して Memoria / Actio に登録します。テストは worktree では絶対に行わず、develop / main の安定ブランチでのみ行う、という原則をハーネス (後述の §8) で強制します。

このうち **develop 確認フロー**は単体で動いています。実装 PR は develop に集め、人間が Discord で `/confirm start <サービス>` と打つと develop 版がビルド・起動され、動作を見て `/confirm ok` すれば main に反映して再起動、までが自動化されています。人間の操作はコマンド 2 回だけです。

- **入口**: タスク md はリポジトリ内ファイル、confirm は Discord コマンド。
- **連携**: Memoria (タスク登録)、Actio (将来)、Excubitor (起動・再起動)。
- **実装状況**: **パイプライン全体は設計のみ** (spec は planned)。ただし部品の develop 確認フロー・委託 (§3)・自走 (§5) は実装済みで、`src/taskflow/` に関連コードが存在します。「全体がどこまで一本につながっているか」は spec からは確定できませんでした。

## 5. 自走支援 — 止まっているセッションを前に進める

AI セッションは回答を返すと入力待ちで止まります。それを放置しないための機構が 3 つあります。

**idle-nudge (待機催促)** は、セッションが最終回答を返してから一定時間 (既定 120 秒) 人間の入力がないと、そのセッションに話しかけたことのある人全員へ Discord / Slack でメンション通知を送ります。「AI が待っているのに依頼者が気付いていない」を救う機能です。

**ゴールアンドゴー**は、明示的に opt-in したセッション限定で、待機を人間への催促ではなくセッション自身の続行につなげます。無入力 300 秒で「ゴールは達成できているか、残作業はないか」を問う注入が入り、セッションが自分で判断して作業を続けます。暴走防止として回数上限 (既定 6 回) と時間上限 (既定 2 時間) があり、人間の入力があれば必ずリセットされます。

**朝タスク仕分け**は、スケジューラが朝に残タスクを仕分けし、停止中のセッションを起こす定期運用です。

- **入口**: idle-nudge は自動。ゴールアンドゴーは API または委託時のオプションで opt-in (既定 OFF)。
- **連携**: Lictor (キー入力検知・transcript)、Discord / Slack (通知)。
- **実装状況**: ゴールアンドゴー・朝タスク仕分けは実装済み。idle-nudge は spec に status フィールドが無いものの、ゴールアンドゴーが「idle-nudge の判定を土台に」実装済みとされているため実装済みと判断しています。

## 6. テスト交通整備と PR ゲート — 壊さないための仕組み

サービスの再起動や起動テストは、複数セッションが同時にやると事故になります。Concordia は「テストを始める前に一報 (claim) を入れる」ルールの正本を持ちます。同じサービスを他のセッションがテスト中なら双方に警告が注入されます (これも助言であってロックではありません)。セッションのブランチ切替も監視されており、切り替えたセッションには運用ルール (Excubitor 経由・本体フォルダのみ・一報) が自動で案内されます。

PR まわりでは、セッションには「実装は作業ブランチで行い、PR を作ったら止まる」というワークフローが起動時に注入されます。CI の結果は Concordia が監視して作者セッションに届き、CI が通った PR は独立サービス Revisor に自動でレビュー依頼が飛びます。マージ待ちの PR は PR キューとして一覧できます。

- **入口**: claim は API (`/cc-test` スキル経由が通例)、PR キューは WebUI / Discord。
- **連携**: Revisor (自動レビュー)、Excubitor (Revisor の解決・サービス起動)、GitHub。
- **実装状況**: 実装済み。

## 7. コストと観測 — いくら使って、何が起きているか

各セッションのトークン使用量・コストが記録され、セッション別・組織全体・時系列で見られます。Codex の週間レート制限の残量も取得しており、あとどれだけ回せるかの目安になります (§2 のフォーラム起動でのテンプレート選択には使われません)。コスト情報は Discord の専用チャンネルにも流れます。

観測面では、セッションログブラウザ (過去セッションの transcript を WebUI で閲覧)、各サービスのエラーを集約して自動修正委託につなげるエラーパイプライン、Concordia 自身の関数実行メトリクスがあります。LUDIARS 各サービスのログは MCP (`concordia-vestigium`) 経由で別セッションからも検索できます。

- **入口**: WebUI (CostFeed / SessionLogs / Reports)、Discord (cost チャンネル)、MCP。
- **連携**: Vestigium (ログ基盤)、Excubitor (サービス状態)。
- **実装状況**: 実装済み。

## 8. 権限と統制 — 誰に何をさせるか

Discord / Slack から Concordia の LLM に触れた人は自動で**社員名簿**に記録されます。権限は 3 段階の役職で決まります: ヒラ社員 (会話とリアクション指示)、管理職 (加えてセッションの起動・終了、PR マージ)、執行役員 (加えてサービス再起動のキルスイッチ)。初回登録は必ずヒラ社員で、昇格は WebUI から人間が行います。判定が配線されていない環境では権限操作はすべて拒否されます (fail-closed)。

AI セッション側の統制は**ハーネスルール**と **Inject マニュアル**です。ハーネスルールは「main への直コミット禁止」「オートマージ禁止」のような allow / block ポリシーで、Inject マニュアルは作業種別 (設計相談 / 実装 / レビュー / テスト / 雑用) ごとにセッションへ差し込まれる作業手順書です。どちらも WebUI のマニュアルページで 1 件ずつ編集できます。

- **入口**: WebUI (Staff / Manuals ページ)。記録自体は自動。
- **連携**: Discord / Slack (ユーザ識別)。Cernere との連携は将来検討。
- **実装状況**: 実装済み。

## 9. マルチ拠点連合 — 本社の外へ

本社の Concordia と別拠点 (site) の Concordia を WebSocket でつなぐ連合リンクです。専用ポートの listener (既定 OFF・opt-in)、事前共有トークン認証、切断中のイベントを貯める outbox、拠点一覧の WebUI、部署スコープ付きの設定配布までが Phase 0〜2 として実装されています。フォーラムのタグで拠点へルーティングする仕組みも入っています。

- **入口**: 環境変数で opt-in、閲覧は WebUI の Federation ページ。
- **連携**: 他拠点の Concordia、Excubitor (ポート登録)。
- **実装状況**: Phase 0〜2 (信頼境界分離・連合リンク・設定配布) は実装済み。それ以降のフェーズと、拠点側での委託実行 (子会社 Delegation) は設計のみ。
