# Discord からの使い方

日常の運用で最もよく触る入口が Discord です。この章では「投稿してセッションを起動する」「返信で指示を続ける」「絵文字で定型作業を発火する」「コマンドを打つ」の 4 つの操作を順に説明します。記載内容はすべて実装コード (`src/discord/` および `src/platform/`) で確認したものです。spec に書かれていても未配線のものは、その旨を明記しています。

## 3 つのフォーラムの使い分け

Concordia は Discord に 3 つのフォーラムチャンネルを自動作成します。名前は固定で **Session**・**Test**・**TaskWorkflow** です。

**Session フォーラム**が人間の作業場です。新規投稿がそのままセッションの起動依頼になり (次節)、起動後はそのスレッド 1 本が状態表示・会話・結果報告のすべてを担います。スレッドには状態タグ (「作業中」「待機」「lost」) と作業内容タグ (設計相談 / 実装 / レビュー / テスト / 雑用) が付くので、フォーラム一覧を眺めるだけで「いま何が動いていて何が待っているか」が分かります。

**TaskWorkflow フォーラム**は委託 (delegation) の記録場所で、1 つの委託 run = 1 スレッドです。委託の発火から進行・結果までがスレッドに集約されます。ここに新規投稿してセッションを起動する場所ではありません (フォーラムの説明文にもそう書かれています)。

**Test フォーラム**はテスト候補の掲示板です。open / draft の PR ごとにスレッドが立ち、PR の現在の head コミットと worktree に同期されます。PR が更新・クローズ・マージされると古いスレッドは閉じられます。

## 投稿してセッションを起動する (spawn-by-post)

Session フォーラムに新規投稿すると、それだけでセッションが起動します。書き方は次のとおりです。

1. **タイトルの先頭にプロジェクトコードを角括弧で書きます** — 例: `[Cc] 委託テンプレの整理`。コードは Concordia の project code registry (`/project-code list` で確認、`/project-code add` で登録) と照合されます。**大文字小文字は区別されます** (`[cc]` は一致しません)。タイトルに無い場合は本文中の `[...]` 表記、それも無ければタイトル・本文に現れるリポジトリ名そのものが手掛かりとして使われます (リポジトリ名の照合のみ大文字小文字を区別しません)。
2. **本文が最初の指示になります。** 依頼内容と完了条件を書いてください。実際にはタイトルと本文の両方がまとめて初回プロンプトとしてセッションに渡されるので、タイトルも雑に付けない方が得です。
3. 投稿すると、Concordia がタイトルと本文を読んで**起動テンプレートを自動選択**し (フォーラム起動可能な委託テンプレートの中から軽量 LLM が 1 つ選びます)、そのテンプレートの設定に従ったエージェントが spawn されます。成功するとスレッドに「Cc がセッションを起動しました (provider: ..., run: ...)」と返信が付きます。

プロジェクトが特定できなかった場合、Concordia はセッションを**起動せず**、「プロジェクトコードまたはリポジトリ名を追記してください」と返信します。ワークスペースのルート直下でセッションを起動することは意図的に禁止されています。また、投稿からの起動には**管理職以上**の役職が必要です (権限が無い場合はその旨が返信されます)。

1 点、第 1 章の記述を訂正します。spec には「Claude / Codex のうち週間レート制限の残量が多い方を自動選択する」という設計がありますが、**この選択ロジックは現行コードでは配線されていません** (実装は存在するものの呼び出されていない、設計のみの状態です)。実際のエージェント選択は上記のテンプレート自動選択によります。

## 返信で指示を続ける

起動後のスレッドへの**通常の投稿は、そのままセッションへの追加指示 (inject) になります**。特別な記法は要りません。「テストも書いて」「その方針で進めて」と書けば、Lictor 経由でセッションの入力に届き、セッションの回答も同じスレッドに返ってきます。投稿者名 (サーバーニックネーム) がラベルとして本文に添えられるので、複数人で同じセッションに話しかけても誰の指示か区別されます。

セッションが終了・ロスト状態のときに投稿すると「This session is <status>; inject is disabled.」と返信されます。この場合は新しい投稿でセッションを立て直してください。

## リアクションワークフロー — 絵文字 1 つで定型作業

メッセージに特定の絵文字でリアクションすると、あらかじめ定義された作業が発火します。リアクションの代わりに**絵文字 1 文字だけを投稿**しても同じです (返信形式ならその参照先、セッションスレッドならそのセッションの直近投稿が対象になります)。発火すると即座に「受付」のリプライが付き、完了時に ✅ (または ⚠️) と結果が返ります。

よく使うものを挙げます (正本は実装の絵文字マッピングで、WebUI の設定ページから上書き・追加もできます)。

| 絵文字 | 何が起きるか |
| --- | --- |
| 👍 🆗 | 実装に着手させる |
| 🙏 | 残作業を洗い出させる |
| 🫶 😴 ✨ | 洗い出した残作業を Memoria に登録する |
| 📲 🆙 👆 | 状況確認 (進捗・ブロック・次の一手) |
| 😄 😊 など笑顔系 | 良い動きをリポジトリの作業メモリに記録する |
| 😡 👎 など怒り系 | 作業を即中断させて反省させる |
| 📝 ✅ ☑️ | Memoria にタスクとして登録する |
| ⏭️ 📤 | 実装タスクを別セッションに委ねる (Memoria 登録) |
| 🤝 | タスクを判定して委託テンプレートで委託実行する |
| 🔀 🚀 | open PR を CI green 確認の上で squash マージし、ブランチ削除と main 同期まで行う |
| 🔄 🔃 | マージ済み確認の上、該当プロジェクトの main を最新へ同期する |
| 👌 👋 | 次セッションへの引き継ぎ資料を作らせる |
| ▶️ ⏩ | 中断していた作業を再開させる |
| 🙄 | Enter キーを強制送信する (入力の取りこぼし救済) |
| 📌 | セッションチャンネルで押すと transcript の中継を再束縛する |
| 🛠️ | そのメッセージ本文 (1 行目 = 絵文字、2 行目 = ラベル、3 行目以降 = プロンプト) を新しいカスタムワークフローとして登録する |

権限は 2 段階です。リアクション自体はヒラ社員でも押せますが、影響の大きいアクションには追加の役職が要ります — 委託 (🤝) とワークフロー登録 (🛠️) は**管理職以上**、PR マージ (🔀 🚀) と main 同期 (🔄) は **merge 権限** (管理職以上) が必要です。不足している場合は黙殺されず、「この操作には◯◯権限が必要です」と本人に返信されます。

なお、リアクションワークフロー全体の ON / OFF は WebUI の設定ページで切り替えられます。発火できるかどうかは社員名簿ベースの権限判定で決まり、判定が配線されていない環境では拒否されます (fail-closed)。かつては環境変数の許可リスト方式で、その設定漏れにより全員拒否になった障害がありました (許可リスト機構自体は現在は廃止済みです)。有効なのに誰の絵文字にも反応しない場合は第 5 章の該当項を見てください。

## スラッシュコマンド一覧

実装されている 16 コマンドです。「セッションスレッド限定」とあるものは、セッションに紐付いたスレッド (またはチャンネル) の中でだけ使えます。

### セッションの起動と終了

- **`/spawn`** — セッションを起動します。委託テンプレートから起動する (`template`) か、プロバイダを直接指定する (`provider`: claude / codex / gemini) かを選べ、`project` `branch` `cwd` `prompt` `model` を添えられます。プロバイダ直指定のときは `project` か `cwd` が必須です。**管理職以上**。
- **`/end-session`** — 現在のセッションを終了します。フォーラムスレッドなら状態タグが「終了」になりアーカイブされます。セッションスレッド限定・**管理職以上**。
- **`/co-relictor`** — セッションを最新版の Lictor で再起動します。引き継ぎ資料を作ってから新セッションを spawn するため、**セッション ID とスレッドは新しくなります**。セッションスレッド限定。
- **`/co-compaction`** — 引き継ぎ型コンパクション (引き継ぎ資料の投稿 → コンテキストのクリア → 続行) を実行します。長時間セッションのコンテキストが膨らんだときに使います。セッションスレッド限定。

### セッションへの操作

- **`/enter`** — セッションに Enter キーを 1 回送ります。CLI 側の対話プロンプトが確定待ちで止まっているときの救済です。引数はありません。セッションスレッド限定。
- **`/co-goal`** — セッションのゴール設定を表示・変更します。`mode` は「完成まで実装 / 範囲限定 / 様子見・確認しながら」の 3 択で、自由文も添えられます。引数なしなら現在値の表示です。セッションスレッド限定。
- **`/cc-skill`** — そのセッションの現在の作業ブランチにあるスキルを呼び出して注入します。候補は autocomplete で出ます (ブランチが一致しないと候補が出ません)。セッションスレッド限定。
- **`/ch_name`** — スレッド名を固定します。以後、Concordia による自動リネームを受け付けなくなります (状態絵文字の反映は続きます)。セッションスレッド限定。

### 情報の表示

- **`/stat`** — Concordia の現在の統計を表示します (自分にだけ見える表示)。
- **`/prs`** — 各セッションが作った PR キューのダイジェストを表示します。
- **`/projects`** — LUDIARS プロジェクトコード一覧をカテゴリ別に表示します。

### タスクとリリース

- **`/mmtask`** — Memoria の残タスクを検索してセッションに注入します。引数なしなら今日期限のタスク、`query` でプロジェクトコード・カテゴリ・キーワード検索です。セッションスレッド限定。
- **`/mmtask-detail`** — タスク ID を指定して詳細を表示します (注入はしません)。
- **`/confirm`** — develop 確認フローの操作です。`list` (確認待ち一覧)、`start <service>` (develop 版に切り替えて起動)、`ok <service>` (main へ反映して main 版で起動し直し)、`ng <service>` (中止して main 版に戻す) の 4 サブコマンドがあります。使い方は第 4 章の手順を参照してください。

### サービス管制と掃除

- **`/ex-run` / `/ex-reboot`** — Excubitor 経由でサービスの起動 / 再起動を行います。`project` は autocomplete で選びます。複数コンポーネントは順次実行され、OK / NG のサマリが返ります。**執行役員のみ**。
- **`/co-clean`** — 終了済みのセッションチャンネルをログ保存した上で一括削除します。

権限が足りないコマンドを打つと「このユーザーにはセッション起動権限がありません (管理職以上が必要)。」のような拒否メッセージが返ります。役職は WebUI の社員ページで変更でき、変更は再起動なしで即時反映されます。また、子会社 (出張先 Bot) のサーバでは `/ch_name` 以外のコマンドはすべて拒否され、依頼は受付チャンネルへのメッセージで行う運用です。

## 補足 — 「お伺い」との関係 (設計のみ・実装中)

第 0 章の用語集にある「お伺い」は、今後この Discord 動線に組み込まれる予定の機能です (2026-08-02 設計確定・実装は委託中で、本書執筆時点ではコードにまだ存在しません)。お伺いは**セッションが人間に聞く**ための仕組みで、Concordia が判断するのではありません。宛先には neco の判断代行である Genius が座り、代行で答えられる問いはそこで返り、代行の手に余る問い (権限・方針転換など) だけが上長へのメンションとして Discord に上がってくる — という設計です。実装が入れば、「AI が回答を返しただけで催促通知が飛ぶ」現行の待機催促は「人間の判断が本当に要るときだけ飛ぶ」形に置き換わる予定です。詳細は実装完了後に本章へ追記します。
