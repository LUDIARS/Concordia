# 運用手順

この章は「やりたいこと」から引く手順書です。各手順は番号付きで、どの画面・どのコマンドを操作するかを具体的に書きます。前提となる概念 (フォーラム、委託、claim など) は第 0〜1 章、画面の詳細は第 2 章、Discord の操作一覧は第 3 章を参照してください。

権限について先に一度だけ書いておきます。セッションの起動・終了と PR マージは**管理職以上**、サービスの起動・再起動 (`/ex-run` `/ex-reboot`) は**執行役員のみ**です。権限が足りない操作は実行されず、その旨が返信されます。

## 手順 1: セッションを起動して作業を頼む

いちばん基本の操作です。入口は 3 つありますが、日常的には Discord のフォーラム投稿が最も手軽です。

**Discord から (推奨)**:

1. **Session フォーラム**を開き、「新しいポスト」を作成します。
2. タイトルの先頭に**プロジェクトコードを角括弧で**書きます。例: `[Cc] 委託テンプレートの整理`。
3. 本文に依頼内容と完了条件を書きます。タイトルと本文の両方が最初の指示としてセッションに渡ります。
4. 投稿します。Concordia が内容を読んで起動テンプレートを選び、セッションを spawn します。成功すると「Cc がセッションを起動しました (provider: ..., run: ...)」の返信が付きます。
5. 以後はこのスレッドに**普通に返信するだけ**で追加指示になります。回答も同じスレッドに返ります。

エージェントやモデルを自分で指定したいときは、フォーラム投稿の代わりに `/spawn` コマンドを使います (`template` または `provider` + `project` を指定)。

**WebUI から**: Monitor ページの組織カードにある spawn フォームで、テンプレートまたはプロバイダ・プロジェクト・ブランチ・初回プロンプトを指定して起動します。起動後の会話はセッション詳細ページ下部の「指示を送る」欄で行います。

**注意**: ワークスペースのルート直下ではセッションは起動しません (プロジェクトの指定が必須です)。また起動直後に Monitor へセッションが現れない場合は第 5 章「成功表示が出るのにセッションが現れない」を参照してください。

## 手順 2: 動いているセッションに追加指示・確認をする

1. Discord なら該当スレッドに書き込みます。WebUI ならセッション詳細の「指示を送る」欄に書きます。どちらも同じ inject 経路で届きます。
2. 進捗が知りたいだけなら、リアクション 📲 (状況確認) を付けるか、WebUI セッション詳細の「stat 依頼」ボタンを使うと、進捗・ブロック・次の一手が返ります。
3. セッションが対話プロンプトで止まっているように見えたら `/enter` (Enter キーを 1 回送る) を試します。
4. セッションがツール実行の許可や選択式の質問を出したときは、Discord のカード (設定で有効な場合) または WebUI セッション詳細のモーダルで回答します。回答するまでセッションは待機します。

## 手順 3: 作業を別のエージェントに委託する

自分で会話しているセッションに全部やらせず、定型作業を別エージェントへ投げる手順です。委託はテンプレート (呼び出し名) 単位で発火します。

**Discord から**: 委託したい内容が書かれたメッセージに 🤝 のリアクションを付けます。内容からタスクが判定され、適切な委託テンプレートで実行・監視まで走ります (管理職以上)。

**WebUI から**:

1. **Delegation ページ**を開き、テンプレート一覧から使いたいテンプレートの「invoke」を押します。
2. 引数パネルが開くので、テンプレートの引数 (対象や指示内容) と、必要なら作業ディレクトリ・ブランチを入力します。
3. Spawn を実行します。run が作成され、下半分の「外注 (作業委託)」欄と TaskWorkflow フォーラムのスレッドで進行を追えます。

**API / MCP から** (セッション内の AI が使う経路): MCP ツール `delegation_invoke`、または `POST /v1/delegation/invoke` に `{ "call_name": "<呼び出し名>", "args": {...} }` を送ります。run の状態は `GET /v1/delegation/runs/:id` で追え、実行中の子セッションへの追加指示は `POST /v1/delegation/runs/:id/inject` で送れます。

run が `spawned` のまま数分動かない場合は第 5 章の該当項 (委託 run が終わらない) を確認してください。

## 手順 4: テストの一報を入れてサービスを再起動する

サービスの再起動・起動テストには運用ルールがあります: **Excubitor 経由・プロジェクト本体フォルダのみ・事前に一報 (claim)**。worktree や複製フォルダからの起動は禁止です。

1. テストを始める前に、Concordia へ claim を入れます。セッション内の AI は `/cc-test` スキル経由が通例で、実体は次の API です:
   ```bash
   curl -s -X POST http://127.0.0.1:11111/v1/testing/claim \
     -H "content-type: application/json" \
     -d '{"session_id":"<自分の session_id>","service":"<サービスコード>","note":"何をテストするか"}'
   ```
2. 応答の `conflicts` を確認します。空でなければ、同じサービスを別のセッションがテスト中です。双方に警告が注入されるので、相手と作業を調整してから進めます (ブロックはされませんが、突っ込むと事故になります)。
3. サービスを再起動します。Discord なら `/ex-reboot` で対象プロジェクトを選びます (執行役員のみ)。複数コンポーネントは順次処理され、OK / NG のサマリが返ります。
4. テストが終わったら release します:
   ```bash
   curl -s -X POST http://127.0.0.1:11111/v1/testing/release \
     -H "content-type: application/json" \
     -d '{"session_id":"<自分の session_id>"}'
   ```
   (service を省略するとそのセッションの claim を全解放します。)

release を忘れても、セッションの終了・ロストで自動解放され、放置 claim は 60 分の TTL で外れます。とはいえ放置 claim が溜まると他セッションへの誤警告の種になるので、終わったら release する習慣にしてください。

## 手順 5: develop に入った変更を確認して main に上げる (/confirm)

実装 PR を develop に集め、人間が一度だけ動作確認してから main へ反映するリリース動線です。人間の操作は Discord のコマンド 2 回だけです。

1. 実装 PR が develop にマージされると、Concordia が確認タスクを積み、PR キューのチャンネルに「確認待ち」が通知されます。`/confirm list` でいつでも確認待ち一覧を見られます。
2. 確認を始めるときは `/confirm start <サービスコード>` を打ちます。develop クローンの同期 → ビルド → main 版の停止 → develop 版の起動、までが自動で行われます (ビルドは分単位かかります)。develop 版が起動できなかった場合は自動で main 版に戻されます。
3. develop 版の動作を実際に確認します。
4. 問題なければ `/confirm ok <サービスコード>`。develop が main に反映され、main クローンが同期され、main 版で起動し直され、確認タスクが完了になります。
5. 問題があれば `/confirm ng <サービスコード> [reason]`。main 版に戻り、確認タスクは保留に戻ります。原因調査と develop の再修正は別途行います。

start / ok / ng は内部で手順 4 の claim / release を自動的に通るため、他セッションのテストと重なれば警告が出ます。

## 手順 6: PR をレビューに回す

Revisor (ローカル PR レビューサービス) へのレビュー提出は、原則**自動**です。

1. セッションが作業ブランチで実装し、コミットを積んで作業を終えます。
2. **セッションが終了すると、Concordia がその作業ブランチを Revisor の local PR として自動提出します** (既定で有効)。提出されない場合も理由付きで記録されます — ブランチが無い、Revisor 未登録のリポジトリ、base ブランチと同一、コミットが無い、同じブランチの open PR が既にある、のいずれかです。
3. セッション終了を待たずにレビューへ出したいときは、手動口 `POST /v1/prs/local` に `{ "session_id": "<セッション ID>" }` を送ります。
4. レビュー結果とマージ待ちの状況は WebUI の **PRs ページ** (Revisor セクション) で確認します。GitHub 側の PR は `/prs` コマンドか同ページで一覧できます。
5. CI が green で内容も良ければマージします。Discord では該当 PR のメッセージに 🔀 リアクション (CI 確認の上 squash マージ + ブランチ削除 + main 同期、管理職以上)。マージ後に作業ツリーの main を最新化したいときは 🔄 です。

なお、この環境の運用ルールとして GitHub 上で直接 PR を作る・マージする経路は使いません。PR は Revisor 経由が正です。

## 手順 7: セッションを終了する

1. 頼んだ作業が終わっていることをスレッドで確認します (残作業が心配なら先に 🙏 で残作業を洗い出させ、必要なら 🫶 で Memoria に登録させます)。
2. セッションのスレッドで `/end-session` を打ちます (管理職以上)。WebUI ならセッション詳細の「停止」でも終了できます。
3. 終了処理の中で、作業レポートの自動生成 (WebUI の Reports に載ります)、セッションログの保存、Revisor への自動レビュー提出 (手順 6) が走ります。フォーラムスレッドは状態タグが更新されアーカイブされます。
4. 溜まった終了済みチャンネルは `/co-clean` でログ保存の上、一括削除できます。

終了ではなく「コンテキストが膨らんだので仕切り直したい」場合は `/co-compaction` (引き継ぎ資料を作ってコンテキストをクリアし、同じセッションで続行)、「Lictor を最新版にして続けたい」場合は `/co-relictor` (引き継ぎ付きで新セッションに乗り換え。スレッドが新しくなります) を使います。

## 手順 8: 止まった・落ちたセッションを引き継ぐ

1. Monitor の **lost セッション一覧**、または Session フォーラムの「lost」タグで、失踪したセッションを確認します (ハートビート 30 分途絶でロスト扱いになります)。
2. Concordia はロストセッションの transcript から最後の作業内容を復元しています。同じ場所で新しいセッションを起動すると、引き継ぎ候補として提示されます。
3. 引き継ぐ場合はその提示に従い、不要なら無視して構いません。ロストセッションの残骸プロセスは猶予期間の後に自動回収されます (第 5 章参照)。

## 補足: 作業完了後の身の振り方と「お伺い」 (設計のみ・実装中)

現在、委託で起動したセッションの「作業が終わったら次はどうするか」は、待機催促 (idle-nudge) とゴールアンドゴーの組み合わせで運用されています。これを置き換える「お伺い (inquiry)」機能が 2026-08-02 に設計確定し、実装が委託中です (本書執筆時点でコードにはまだ存在しません)。

設計の骨子だけ書いておくと — お伺いは**セッションが人間に聞く**ための取り次ぎです。作業完了時にセッションが「次に進んでよいか」をカテゴリ付きで Concordia に諮ると、Concordia は判断せず、neco の判断代行である Genius に取り次ぎます。代行で答えられればセッションはそのまま進み (残業)、代行の手に余る問いだけが上長へのメンションとして人間に上がり、人間を待つ間だけ催促タイマーが張られます。Genius が不在ならセッション自身の通常判断に委ねられます。実装が入り次第、この節は正式な手順に書き換えます。
