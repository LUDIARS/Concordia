# トラブルシューティング

この章は、Concordia の運用で**実際に起きた障害**の記録 (`spec/plan/problem_logs/` 配下) だけを材料にしています。架空の症状は載せていません。各項目は「症状 → 原因 → 対処」の順で書き、障害記録の日付を添えています。対処欄の「修正済み」は恒久修正がコードに入っていることを、「未解決」は本書執筆時点 (2026-08-02) で再発しうることを意味します。

読み方のコツを先に 1 つ。Concordia まわりの障害の多くは「エラーが出る」ではなく「**何も起きない・成功と表示されるのに動いていない**」という形で現れます。無反応に遭遇したら、まず本章の該当症状を探し、それでも当たらなければセッション詳細画面のイベントタイムラインと Concordia 本体のログを見てください。

## 起動しない・登録されない系

### 「Spawned (pid: ...)」と成功表示が出るのにセッションが現れない

- **症状**: Discord の `/spawn` などで「Spawned from ... (pid: 14420)」と成功メッセージが出るのに、Monitor にセッションが登録されず、スレッドでの会話もできない。(2026-07-24 の障害記録)
- **原因**: 2 系統ありました。1 つは Windows のパス破損 — 保存された作業ディレクトリ引数が `E:DocumentArsConcordia` のようにバックスラッシュを失っており、「cwd が存在しない」で起動に失敗していたもの。もう 1 つは Lictor ランタイム自体の不全 — `node-pty` のインストールが不完全、あるいは Lictor の起動パスが壊れたチェックアウトを指していると、プロセス (PID) は生まれるのにセッション登録まで到達しません。かつての `/spawn` は 12 秒待ってセッションが無くても PID だけで成功文言を出していました。
- **対処**: Lictor ランタイム側は復旧済みで、Discord の表示も「12 秒以内に登録が確認できなければ未確認と表示する」よう変更されています。ただし Windows パス保全の恒久修正は要件段階のため、**再遭遇したらまず Lictor の実行環境 (node-pty・起動パス) を疑い、次に spawn 引数に保存されたパスを確認**してください。状態は「調査中」です。

### WebUI からの spawn が「authentication_not_configured」で失敗する

- **症状**: WebUI のセッション起動が `spawn failed: authentication_not_configured` で拒否される。(2026-07-24)
- **原因**: 管理系 API が fail-closed (認証未設定なら拒否) 化された一方、ローカルのサービス環境変数に `CONCORDIA_ADMIN_TOKEN` が注入されていないためです。設定漏れであって、コードの故障ではありません。
- **対処**: **未解決** (ローカル環境での認証契約の決め直しが要件化されている段階)。当面はサービス側の環境に admin token が入っているかを確認してください。この症状はテスト一報 (claim/release) など他の管理系操作にも波及します。

### フォーラム投稿が「起動テンプレのタグが必要です (利用可能なテンプレなし)」で行き止まる

- **症状**: Session フォーラムに投稿してもセッションが起動せず、利用可能テンプレートが 1 つも無い旨が返る。(2026-07-16)
- **原因**: フォーラム起動可能な (引数不要の) 委託テンプレートがデータベースに seed されていない状態。初期構築や再シード直後に起きます。
- **対処**: 修正済み。引数不要の Claude / Codex 用 forum-ready テンプレートが seed され、フォーラムタグもレイアウト確認時に自動整合されるようになりました。それでも同症状が出たら、WebUI の Delegation ページでフォーラムタグ付きテンプレートが存在するか確認してください。

### worktree で起動したセッションが信頼確認ダイアログで止まる

- **症状**: worktree 内で spawn されたセッションが、初回に trust / 設定の対話ダイアログを出したまま進まない。プロジェクト固有のスキルやメモリも見えていない。(2026-07-19)
- **原因**: worktree を作って cwd にするだけの実装だったため、gitignore されている `.claude` などの設定ディレクトリが worktree に複製されていませんでした。
- **対処**: 修正済み。spawn 前に `.claude` / `.codex` / MCP 設定と主プロジェクトのメモリを worktree へコピーし、コピーに失敗した場合は黙って進まず worktree を削除して失敗を可視化するようになっています。

## 無反応系 — 「有効なのに何も起きない」

### リアクションを付けても何も起きない

- **症状**: リアクションワークフローが有効と表示されているのに、登録済みの絵文字を付けても何も実行されず、エラー応答すら無い。(2026-07-16)
- **原因**: リアクション実行は deny-by-default (許可リストに載った人だけ実行可能) で、その許可リスト `CONCORDIA_REACTION_WORKFLOW_DISCORD_USERS` がどこにも設定されていない = 全員拒否になっていたためです。管理画面には有効/無効フラグしか出ておらず、許可リストが空であることが見えませんでした。
- **対処**: 障害記録の時点では未解決でしたが、その後この環境変数の許可リスト機構自体が**廃止**され、発火権限は社員名簿の役職判定に置き換わりました。設定ページの「リアクションWF」セクションには「実行可能ユーザーなし」の警告表示も入っています。現在同様の無反応に遭遇したら、同セクションの有効化状態と警告、そして社員ページで自分が名簿に載っているかを確認してください。

### message optimize を OFF にしても作業内容が Discord に出ない

- **症状**: 「作業内容の最適化 (要約)」設定を OFF にしたのに、AI の途中経過 (commentary) が Discord に流れず、ON のときと同じ表示のまま。(2026-07-16)
- **原因**: 中継処理が設定フラグを評価する前の段階で、最終回答以外のフレームを無条件に破棄していました。
- **対処**: 修正済み。OFF を明示した場合は途中経過も中継されます。ON のときに要約だけが出るのは正常な挙動です。

### 委託 run が「spawned」のまま永久に終わらない

- **症状**: フォーラムには「セッションを起動しました」と出るのに、委託 run の状態が `spawned` から動かず、完了も失敗もしない。(2026-07-16)
- **原因**: Codex CLI の出力形式 (JSONL) が更新され、Concordia 側のワーカーが旧形式しか解釈できなくなっていたため、セッション登録も終端状態の更新も行われませんでした。
- **対処**: 修正済み (新旧両形式に対応し、終了時に必ず completed / failed を記録)。ただし **CLI 側の形式変更のたびに再発しうる系統の障害**です。run が spawned のまま数分動かなければ、この線を疑ってください。委託 run の状態表示が当てにならない場合の一般則は「PID の生存と子セッションの状態で判定し、3 分で見切る」です。

## 二重起動・意図しない挙動系

### 1 回の操作でエージェントが 2 体起動する

- **症状**: フォーラドでの 1 回の spawn 操作から、数秒差で 2 体のエージェント (例: codex と claude) が起動し、しかも Concordia 自身が投稿した本文がタスクとして注入される。(2026-07-25)
- **原因**: 明示的な `/spawn` と、フォーラムの新規スレッド検知による自動 spawn (spawn-by-post) が互いを識別できず、両方が発火していました。相関用の一時マーカーはキー不一致で機能していませんでした。
- **対処**: 修正済み (Concordia が作るスレッドには専用タグを作成時に原子的に付与し、自動 spawn 側がそれを見て早期に無視する方式)。マージ・実機確認待ちの段階で記録されています。

### セッションが指示していないテスト実行やマージまで勝手に進む

- **症状**: 作業を頼んだだけのセッションが、指示していないサービスの起動テストや PR のマージまで実行してしまう。ほかに「作業ディレクトリがプロジェクトではなくワークスペースルートになる」「要求したブランチが登録されない」なども同時期に報告されています。(2026-07-19、5 件の再発報告)
- **原因**: 個々のプロンプトの問題ではなく構造的なもので、セッションの完了ポリシー (どこまでやって止まるか) が複数のテンプレートや文脈注入に矛盾して分散していたこと、cwd のフォールバックがランチャー自体に埋まっていたことが挙げられています。
- **対処**: 3 アウト則に基づき、中央の spawn ガードと単一の完了ポリシーへ置き換える設計是正が行われました。それでもセッションが越権的に動いた場合は、スレッドで明示的に止めてください (人間の発話が最優先の指示になります)。

### フォーラム起動セッションの作業ディレクトリがホームディレクトリになる

- **症状**: フォーラム投稿から起動したセッションが、プロジェクトのルートではなくユーザのホームディレクトリで動いている。(2026-07-18)
- **原因**: フォーラム経由の spawn だけがプロジェクトコード解決失敗時の cwd 決定処理 (共通リゾルバ) を通っていませんでした。
- **対処**: 修正済み。フォーラム spawn も共通の cwd リゾルバを通ります。予防としては、**投稿タイトルにプロジェクトコードを必ず入れる**ことが確実です。

## Concordia 本体の不調系

### Concordia が断続的に応答しなくなる

- **症状**: 「Cc が断続的に落ちる」ように見える。実際にはプロセスは生きていて、ヘルスチェック (`/health`) が HTTP タイムアウトになる。(2026-07-15)
- **原因**: セッション停止処理の同期的なプロセス kill (`taskkill`) を API ルートやタイマーが直接呼んでおり、シングルスレッドのイベントループ全体が止まっていました。
- **対処**: 修正済み。停止要求は永続キューに積まれ、別プロセスのワーカーが処理します (管理系の停止 API は「202 受付」を返してすぐ戻ります)。なお Concordia のイベントループ停止はこの障害以外にも過去に複数の原因で起きているため (transcript の同期全読みなど)、応答遅延を見たら「落ちた」ではなく「イベントループが詰まっている」を第一仮説にしてください。

### 長時間運用で CPU とメモリが際限なく増える

- **症状**: 数日規模の連続稼働でホストの CPU が 40〜100% に張り付き、node プロセスが 90 件 / 8.2GB といった規模まで肥大して、最終的に Windows の再起動が必要になった。(2026-07-18 調査レポート)
- **原因**: 主因は長寿命セッションと入れ子 spawn によるプロセスの増殖 (1 つの Lictor ツリーに最大 136 の子孫)。副次要因として、ロスト状態のセッションのプロセスが回収されず残り続けていたこと、期限切れの放置 claim が 131 個溜まっていたことが挙げられています。
- **対処**: ロストセッションのプロセスについては修正済み (有限の復帰猶予の後、Lictor プロセスと確認できたものだけ回収)。プロセス増殖自体への恒久対処は追跡課題として残っています。長期運用では、Monitor でロスト・長寿命セッションを定期的に確認し、不要なものは終了させるのが現実的な予防です。

### ロストしたセッションのプロセスが生き続けている

- **症状**: 状態が「ロスト」のセッションなのに、その PID と十数個の子孫プロセス (各 0.7GB 程度) が残り続け、リソースを食い続ける。(2026-07-18)
- **原因**: プロセス回収 (reaper) が、ロストセッションの PID を「復帰するかもしれない」と無期限に保護していました。
- **対処**: 修正済み。有限の猶予期間を過ぎ、WebSocket 接続が無く、PID とコマンドラインが Lictor 本体だと確認できた場合のみ回収されます。

## Discord 固有の症状

### コマンドに「アプリケーションが応答しませんでした」と出る

- **症状**: `/end-session` などのコマンド実行時に Discord が「アプリケーションが応答しませんでした」と表示する。(2026-07-06)
- **原因**: Discord はコマンドへの 3 秒以内の応答を要求しますが、interaction の到着自体が 13.9 秒遅延していたケースが記録されています。処理が実は成功していることもあります。
- **対処**: ハンドラ側は冒頭で応答猶予を確保する (defer) よう修正済みですが、gateway 遅延そのものは外部要因として残ります。この表示が出たら、**まず操作が実際には反映されていないかを Monitor 等で確認**してから再実行してください。

### PR のテスト開始が「HTTP 409」「ビルドに失敗: spawn EINVAL」で失敗する

- **症状**: Discord からテスト開始を指示すると「テスト開始に失敗: HTTP 409」、Concordia ログには `spawn EINVAL`。(2026-07-16)
- **原因**: Windows 上で `npm.cmd` をシェル無しで直接 spawn すると、現行の Node.js では EINVAL になります。さらに Discord 側のヘルパーがエラー本文を捨てて HTTP ステータスしか表示しないため、原因が読めませんでした。
- **対処**: **未解決** (ComSpec 経由での起動とエラー本文の保持が要件化されている段階)。同様の `spawn EINVAL` は Windows 環境の npm 実行全般で起こりうるので、ログにこの文字列を見たらまず Windows のプロセス起動方法を疑ってください。

### Codex への委託が「windows sandbox: orchestrator_helper_exit_nonzero」で全滅する

- **症状**: 委託でセッションの起動と登録までは成功するのに、最初のコマンド実行すら `orchestrator_helper_exit_nonzero` で失敗し、作業が一切進まない。(2026-07-23)
- **原因**: Codex CLI の Windows サンドボックスのヘルパープロセス側の問題です。Concordia のテンプレート・spawn・worktree 処理は無関係と切り分け済みですが、引き金 (同時起動・承認ポリシー・一時的な ACL) は未確定です。
- **対処**: **未解決**。再発時は単発での再現確認 → 逐次起動 (同時に複数投げない) → 有限リトライ、の順で切り分けます。サンドボックスの無効化は許容されていません。

## 表示・体裁の既知事項

いずれも修正済みですが、「そういう仕様だったのか」と分かるよう記録しておきます。

- **セッション詳細の作業内容に内部 JSON が並ぶ** (2026-07-16): 内部イベント (raw / tool / thinking) は現在「内部イベント」トグルに折りたたまれています。作業更新だけ読みたいときはトグルを開かないでください。
- **「🔄 作業中…」投稿が通知ノイズになる** (2026-07-18): フォーラムでは作業中の投稿は廃止され、スレッドの状態タグで表現されます。作業中かどうかはタグを見てください。
- **委託テンプレートの絵文字がスレッド名に出ない** (2026-07-18): 修正済み。スレッド名は「絵文字 [プロジェクトコード] 要約」の形式です。
- **コンパクション警告が文字化けする** (2026-07-06): 固定文言の文字化けで、修正と再発防止テストが入っています。
- **ユーザ投稿から起動するとステータス表示が保存されない** (2026-07-23): bot が他人の投稿を編集できないという Discord の制約が原因で、現在は投稿を編集せず webhook で別のステータスメッセージを立てる方式に修正済みです。

## それでも分からないとき

1. **セッション詳細ページ**のイベントタイムラインで、最後に何が起きたかを確認します。inject が届いているか、ハートビートが途絶えていないかが見えます。
2. **Concordia 本体のログ**を確認します (Excubitor のログビューア、または `concordia-vestigium` MCP からの検索)。
3. 症状が新規なら、`spec/plan/problem_logs/` に日付付きの記録を残すのがこのプロジェクトの流儀です。本章もその記録から作られています。
