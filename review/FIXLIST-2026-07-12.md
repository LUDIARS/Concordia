## P1: 最優先 — データ被害・無認証実行に直結

### P1-1. DB 肥大の解消: 旧 observability テーブル DROP + retention 配線

- **場所**: `src/db/schema.ts:257-406` / `src/db/transcript-logs-repo.ts:154-163` / `src/db/sessions-repo.ts:323-340` (sweeper purge) / `src/db/rules-repo.ts:172` / `src/db/stats-repo.ts:91`
- **現状 (実測値, 2026-07-12)**: `concordia.db` = **803MB**。内訳の主因:
  - `liveness_history` = **1,093,318 行** ← Excubitor へ移管済み (core.ts:411 に「2026-05-31 分離」と明記)、コード参照ゼロの孤児
  - `service_instance_logs` = 130,359 行 ← 同上、孤児
  - `transcript_logs` = 770,772 行 ← retention 未配線 (`deleteOlderThan` は「呼ばれていない」と自認する dead code)
  - `rules_log` = 442,926 行 ← INSERT のみ、DELETE 経路ゼロ
  - `session_stats` = 65,398 行 ← `purgeOlderThan` 実装済みだが呼び出し元ゼロ
  - 対照的に協調データ本体は健全: `session_events` 35,658 / `sessions` 504
- **修正方針**:
  1. `schema.ts:257-406` の Excubitor 移管済みテーブル群 (`hosts` / `services` / `service_instances` / `liveness_history` / `service_instance_logs` / `error_rules` / `error_tasks` / `auto_fix_runs` / `audit_log`) の DDL を削除。**削除前に `src` / `web/src` / `tools` / `plugins` / `tests` 全域を Grep して参照ゼロを再確認**すること (schema.ts 以外に無いはず)。
  2. 実 DB に対して `DROP TABLE IF EXISTS ...` + `VACUUM` を行う起動時 one-shot マイグレーションを用意する (コード側で完結させ、手動 SQL 実行を担当者に強いない)。**実 DB への適用は「作業前ルール 2」に従い、バックアップ後に行う**。
  3. `transcript_logs` / `rules_log` / `session_stats` の retention を sweeper の `purgeStale` 経路 (sessions-repo.ts:323-340) に追加配線。保持期間は既存の `session_events` / `session_reports` の GC 方針 (90日) に合わせる。TTL は env で上書き可能に (既存 `readPositiveIntEnv` パターン準拠)。
  4. `transcript-logs-repo.ts:154-163` の dead `deleteOlderThan` を、配線するなら生かす / しないなら削除。
- **受入基準**: DROP + VACUUM 後の DB サイズが大幅減 (数百MB回収)。sweeper 1 周後に上記3テーブルの古い行が消える vitest を追加。`npm run lint` / `npm test` グリーン。
- **注意**: DROP と retention はコミットを分けてよい (同一ブランチ内)。VACUUM は WAL と競合するので cost-worker 等を止めてから。実 DB への破壊操作 (DROP+VACUUM の適用) は最終確認を人間に委ね、コード実装とマイグレーション整備までを担当範囲とする。

### P1-2. 認証境界の統一: 危険ルートを admin ゲート内へ

- **場所**: `src/app.ts:79-81` (認証ミドルウェア適用範囲) / `src/bootstrap/core.ts:251-262` (起動拒否メッセージ)
- **現状**: `adminAuthMiddleware` は `/v1/admin/*` と `/v1/sweeper/run` のみ。以下の同等以上に危険なルートが**無認証**:
  - `POST /v1/sessions/:id/inject` (稼働中エージェントへプロンプト注入)
  - `POST /v1/delegation/invoke` (セッション spawn)
  - `DELETE /v1/sessions/:id` (kill + 削除)
  - `POST /v1/processes` 系 (→ P1-3 で別途)
  - `spawn` だけは独自 bearer (token.ts) で守られており方針不統一
- **修正方針**: 上記の副作用系ルートを `adminAuthMiddleware` の対象に含める (パスプレフィックス追加、または個別 middleware 適用)。**loopback + token 空なら素通しの既存挙動は維持**してよい (ローカル運用を壊さない)。あわせて core.ts:254 の起動拒否メッセージを、これら spawn/inject/delete 系の露出も警告する文面に更新。
- **受入基準**: 非 loopback bind + admin token 設定時、上記ルートが 401 を返す vitest。loopback 時は従来どおり通る。
- **注意**: web フロントがこれらを叩いているなら (Grep で確認: `inject` / `delegation/invoke` / `DELETE .../sessions`)、loopback 経由なので token 空で通り、影響なし。トンネル経由アクセスのみ塞がる想定。

### P1-3. `POST /v1/processes` 系の無認証 RCE を封じる

- **受入基準**: `POST /v1/processes` / `stop-all` / `DELETE :name` が削除 or admin gated。`processes list` / `logs` (GET) は従来どおり動作。
- **注意**: `dev-process.md` の auto_start 経由の正規起動フロー (`src/processes/manager.ts`) は別物なので壊さない。

### P1-4. reaction-workflow の権限スキップ実行にリアクター allowlist

### P1-5. 子会社ガードのボタン/モーダル経路バイパスを塞ぐ

- **場所**: `src/discord/commands.ts:99-119` / `src/discord/ingress.ts:83-87, 106-125` / `src/discord/control.ts:54-64, 94-99, 175-188`
- **現状**: 子会社 guild の slash command は `commandName in interaction` で拒否するが、ボタン/セレクト/モーダル (`ctrl:*`) は `commandName` を持たずガードを素通り。かつ `isControlTrigger` (「control」テキスト) が subsidiary intake ゲート判定より**前**に評価される。結果、子会社 guild の任意メンバーが「control」と打つだけで本社の全 active セッション一覧を閲覧し、`ctrl:spawn` (cwd 自由入力) で本社セッション spawn、`ctrl:end-session` で本社セッション終了ができる。

- **受入基準**: 子会社 guild からの「control」テキスト・`ctrl:spawn`・`ctrl:end-session` がすべて拒否される vitest。本社 guild では従来どおり動作。

### P2-7. 周期ループの障害封じ込め (連続失敗の自動停止 + 通知)

- **場所**: `src/bootstrap/core.ts:614-669` (`startPostListenBackground` — `trackPostListenHandle` 管理下の 15 本超の周期ループ) / 各ループ実装 (`src/sweeper.ts` / `src/control/reaper.ts` / `src/metrics/loop.ts` / `src/stat/scheduler.ts` / `src/pr/*.ts` ほか)
- **現状**: 各ループの tick 内 try/catch は概ねあるが (`metrics/loop.ts:33-47` 等)、(a) **壊れ続けるループが warn を吐き続けるだけで誰も気づかない**、(b) try/catch の無い非同期経路の未捕捉例外が**プロセス全体を道連れ**にしうる、の 2 態様が残る。1 ループの破綻が全機能 (hooks 受信・Discord 応答・sweeper) の破綻に化ける構図。

### P2-8. event-loop lag 警告の通知配線 (warn ログ止まりの解消)

- **場所**: `src/metrics/event-loop-lag.ts:67-72` (p99 > 200ms で warn ログのみ) / `src/metrics/loop.ts:33-48` (snapshot は host_metrics へ格納済み)
- **現状**: lag 計測 (3軸計画 T0-5) は実装済みで p99>200ms の warn も出るが、**ログに埋もれて誰も見ない**。「何かがイベントループを塞いでいる」ことをリアルタイムに知る経路が無く、プロセス分離の要否判断 (次にどこを切り出すか) の証拠も収集されっぱなし。
- **修正方針**: 閾値超過が M 回継続したら chat (system channel) / Excubitor へ通知。通知には直近の遅い HTTP リクエスト (`perf` ログ相当の情報) を添えて「何が塞いだか」の初動を短縮する。閾値・継続回数は env ノブ (既存 `readPositiveIntEnv` パターン)。
- **受入基準**: 閾値超過の連続で通知が 1 回 (cooldown 付き) 出る vitest。正常時は無音。
