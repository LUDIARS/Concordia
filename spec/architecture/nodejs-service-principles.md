# Node.js 採用とサービス原則

## 採用方針と適用範囲

**Concordia のサービス実装には Node.js / TypeScript を採用する。**
2026-09-12 の neco による採用方針・原則の仕様化指示を根拠とする。
本書は今後の設計・変更で守る規範であり、既存実装がすべて適合済みという宣言ではない。
frontmatter の `planned` は原則の実装反映が未完了であることを示す。

適用対象は backend、チャット連携、委託・集計・巡回などのサービス内処理とワーカー。
外部 AI の推論エンジンや他サービスの実装言語は規定しない。
サポート対象の Node.js LTS を使用し、対応範囲は `package.json`、実行構成はサービス所有の
`excubitor.catalog.yaml` と設定仕様を正本にする。本書に特定のバージョンやポートを複製しない。

## UX から見た採用理由

Concordia は「全てのAIと人間が調和する空間」を提供するハーモナイザーである。
会話・関心・意図を共有し、権限と合意を守り、途中停止しても仕事を見失わないことを重視する。
利用者の価値とシナリオの正本は [プロダクト UX](../ux/product.md)。

HTTP / WebSocket、チャット、外部サービスとの非同期 I/O が中心の処理には Node.js が適する。
既存の TypeScript、通信 adapter、ワーカーと lease の実装を継続利用できる。
ただし、長い JavaScript 処理や同期 I/O を同じイベントループで実行すると、別の依頼への応答も
遅れる。採用の前提は、受付・回答・状態確認の経路を短く保ち、重い処理と障害の影響を隔離すること。
これは [Node.js のイベントループ設計指針](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)
に沿う。`async` 宣言だけで内部の同期処理が非同期化されるとは扱わない。

| 守る体験 | 対応する価値 | サービスに必要な性質 |
|---|---|---|
| 依頼・回答が受理されたか分かる | UX-CC-W1/W4 | 短い受付、対象と認可の確認、受理と実行完了の区別 |
| 集計・巡回中にも会話と状態確認ができる | UX-CC-W4/W5 | 負荷上限、優先順位、障害分離 |
| 中断後も回答待ちと仕事の現在地が残る | UX-CC-W2/W5 | 永続状態、依頼同一性、再接続時の照合 |
| 成果と配達の状態を取り違えない | UX-CC-W3/W4 | 状態所有者、証拠、再送可能な配達 |

## 必須原則

以下の ID はレビュー時の参照に使う。自動検証済みのゲート ID ではない。
業務上の権限・状態遷移は [DDD 方針の CC-INV-01〜08](ddd.md#業務不変条件) を併せて守る。

| ID | 守るルール |
|---|---|
| CC-NODE-01 応答性 | 対話・受付・状態確認の経路で、長時間の CPU 処理、同期的な外部コマンド、上限のないファイル走査・JSON 処理を行わない。非同期 I/O、処理量の制限、分割実行、ワーカーへの移譲を選ぶ。起動時の同期処理は readiness 前に限定し、量と待機上限を明示する。 |
| CC-NODE-02 負荷制御 | キュー長、同時実行数、入力・応答サイズ、外部 I/O の期限を制限する。上限時は待機・拒否・縮退を明示し、メモリに無制限に積まない。人間の回答・停止指示と通常の巡回の優先順位を定義する。 |
| CC-NODE-03 仕事の寿命 | 再起動を越える仕事は外部副作用の前に依頼 ID と状態を永続化する。受付、起動、結果確認、結果保存、配達を別の事実として扱う。再試行前に同一依頼と既存結果を照合し、応答喪失を失敗確定や再実行許可へ変換しない。 |
| CC-NODE-04 人間待ち | 回答待ちを HTTP 接続・WebSocket 接続・一つの Promise の生存期間だけに保存しない。質問 ID、対象・内容版、回答権限、待機状態を保存し、再接続後も参照・回答できるようにする。接続のタイムアウトと業務上の回答期限を分け、期限切れを承認にしない。 |
| CC-NODE-05 障害境界 | 受付、協働状態、実行、配達の責任を分ける。負荷・障害・再起動の影響が異なる処理は必要な単位でプロセスを分離する。各プロセスは担当、mode、依存、停止時に失われる機能を明示し、黙って別プロセスへ処理を戻さない。 |
| CC-NODE-06 状態と DB | 業務状態の所有者と更新契約を定め、他の処理から直接状態機械を迂回しない。DB transaction を短くし、外部 I/O や人間待ちを含めない。同期 DB API の実行・ロック待ち・checkpoint もイベントループの時間を使うものとして扱う。プロセス分割だけで共有 DB の競合が解消したと判断しない。 |
| CC-NODE-07 配達と再接続 | 通知の作成、送信試行、配達確認を区別する。重要な配達は保存済み状態から再送・照合できるようにする。インプロセス eventBus や一回の WS push を唯一の記録にしない。重複排除と、切断後に差分または現在状態を取得する契約を設ける。 |
| CC-NODE-08 所有権と停止 | lease 喪失後は新しい仕事を取得しない。通常停止は受付・取得停止、実行中の結果処理、資源解放の順を定める。待機上限を超える場合は結果不明の照合方法を残す。子プロセス、接続、timer、listener、DB は生成した所有者が正常・異常・途中終了の全経路を管理する。 |
| CC-NODE-09 異常終了と復旧 | 処理単位で回復できるエラーはその境界で扱い、失敗を記録・通知する。`uncaughtException` 後は通常の業務処理を継続しない。致命的異常では最小限の同期的な診断・後始末で終了し、Excubitor による外部監督と、再起動後の永続状態照合で復旧する。壊れたプロセス内の非同期保存の成功に復旧を依存させない。 |
| CC-NODE-10 観測と構成 | プロセス生存、受付可能、依存障害、仕事の滞留、配達失敗を区別して観測する。mode・接続先・制限値の正本を一本化し、実配線との一致を確認する。設定不足を空の成功や無言の no-op に変換しない。ログには相関 ID と失敗理由を残し、秘密や不要な本文は載せない。 |

CC-NODE-09 は [Node.js の未捕捉例外に関する公式指針](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly)
に従う。通常停止時の drain と、状態を保証できない致命的異常時の終了を混同しない。
再起動は回数・間隔の上限と復旧不能時の表示を設計し、即時再起動の無限ループにしない。

## 責任と配置

| 責任 | 所有するもの | 配置の考え方 |
|---|---|---|
| 対話の入口 | 入力検証、認可、依頼の受理、状態照会 | Web / Discord / Lictor 等の入口を短く保つ |
| 協働の状態 | 対象、参加者、合意、回答待ち、依頼・実行・結果の遷移 | 正本の更新契約を集約する |
| 実行担当 | 委託、集計、巡回、外部 CLI と結果照合 | 永続キューと所有権を使い、重い処理は隔離する |
| 配達担当 | 会話・通知の配送と再接続 | 配達失敗が業務結果を取り消さない境界にする |
| 外部監督 | サービスプロセスの起動・停止・再起動 | Excubitor が所有し、Cc 内に第二の監督者を作らない |

この責任表は一対一のマイクロサービス分割を要求しない。同一リポ内で責任を分け、隔離が必要な
境界を少数の実行プロセスにする。CPU 負荷の高い JavaScript には worker threads も候補となるが、
通常の非同期 I/O のために無条件で増やさない。独立した再起動が必要な境界はプロセス分離で扱う。
[worker threads の公式説明](https://nodejs.org/api/worker_threads.html)を参照する。

## 代替案と再評価条件

- Node.js を維持し、既存の adapter・ワーカー・lease を使って上記原則へ段階的に揃える。
- 言語の全面移植は初期方針としない。CPU・メモリ・配布条件などの制約が測定で明らかになったら、
  対象処理を限定して他言語の採用効果、移行費用、復旧契約への影響を比較し、理由を記録する。
- SQLite の継続可否は Node.js の採否と分ける。単一ホストで短い書込処理なら候補に残し、
  複数ホストや書込競合が制約になればクライアント・サーバ型 DB を比較する。
  SQLite は一つの DB ファイルに同時 writer が一つという特性がある。
  [SQLite の用途指針](https://www.sqlite.org/whentouse.html)を参照する。
- 常駐方式は継続的な対話・接続に適するが、プロセスのメモリを仕事の唯一の保存先にはしない。

以下は 2026-09-12、本体 main の `f2d5dc82ea52678a10f781b234705ad925f5c297` を
参照した静的な所見。実際の稼働 dist・環境 override・性能との一致は未確認。

| 確認箇所 | 現在地 | 今後の確認・整備 |
|---|---|---|
| `src/bootstrap/core.ts` | HTTP/WS、DB、Bot、委託キューと多数の定期処理の組立てが集中 | 行数ではなく負荷と資源寿命から責任・実行境界を整理する |

| `src/chat-worker.ts` / `workflow-worker.ts` | 独立ワーカーの入口と lease が存在 | 分離済みと一括判定せず、担当する仕事・復旧・配達の範囲を確認する |

まず重要な受付・回答・状態確認の経路を特定し、既存の

文書の追加自体ではランタイム設定、再起動方針、DB、プロセス配置を変更しない。

## 受入条件と未測定事項

今後この境界を変更する PR は、適用する CC-NODE / CC-INV / UX 価値 ID、状態所有者、
中断・再試行・停止・再接続の回復方法、実施した検証と未実施項目を示す。
少なくとも次の利用者の状態を維持できるように設計する。

1. 集計や外部ツールが遅くても、受理結果と仕事の現在地を確認できる。
2. 回答待ちは接続切断・再起動を越えて残り、権限のある回答だけを対象版へ適用する。
3. 結果不明の再試行で仕事を重複作成せず、照合不能なら確認事項として表示する。
4. 所有権喪失・停止後に新しい仕事を始めず、残った結果を後続担当が照合できる。
5. 配達失敗と業務結果を分け、再接続で状態を回復できる。

受付確認時間の p95/p99、イベントループ遅延、DB 実行・待機時間、最古のキュー待機時間、
再起動後の未照合件数、通知遅延を評価候補とする。許容値、測定期間、負荷条件、単一ホスト前提、
回答の保持期間と復旧時間の目標は未決定であり、実測後に運用担当とプロダクト責任者が定める。
テスト・負荷試験・サービス操作の実行権限は人間の指示に従い、本書の受入条件から推定しない。

UX と本書の正本はリポジトリの `spec/`。Praeforma / Anatomia は同じ文書 ID・内容版を参照する。
調査時点では Praeforma の Concordia 登録の UX 欄が空、Anatomia context には本体配下の
入れ子 worktree の資料が混入していた。解析対象と正本の対応を確認してから参照を整備し、
登録・解析・人間承認・実装適合をそれぞれ別の事実として記録する。
