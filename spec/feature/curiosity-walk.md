# 散歩セッション

> 2026-08-20 neco 指示。「ランダムなタイミングで起きる問いかけと議論が多分発明に
> つながるんじゃないかな理論」「他のサービスに興味を持つとかも良い」。

## 0. 何を装置にするのか

[inquiry.md](inquiry.md) のお伺いは **1 つの
case の中で詰まった点**を人間に問う。決定を得るための問いであり、答えは必ず要る。

散歩セッションはその双子で、目的が逆になる。**決定を求めない**。1 つの case の中を
掘らず、**互いに関連の薄い 2 件を同じ画面に並べて**、片方の制約をもう片方に当てたら
どうなるかを言語化させる。外れることが仕様で、当たりは 1〜2 割で足りる。

設計上の要点は「ランダム」の置き場所である。乱すのは**時刻ではなく組み合わせ**。

- **素材のランダム性が本体**。無関係な 2 件が並ぶと、制約を移す操作が起きる。
- **時刻のランダム性は添え物**。人間が実行モードでない瞬間に当てるための安い近似。
- **問われること**が要る。並べるだけでは滑る。「どちらを採るか」ではなく
  「この制約をあっちに持っていったらどうなるか」を書かせるから出る。

## 1. 素材の引き方

素材源 (いずれも読むだけ):

- 別サービスの `spec/feature/*.md` と `spec/tasks/*.md` (LUDIARS のローカルクローン)
- 直近マージされた local PR のタイトルと差分要約
- Director case の goal / handoff_note
- Excubitor カタログ上の稼働サービス (何が動いているか)

2 件は **遠さ重みつきでサンプリング**する。遠さは次の順で決める。

1. 別リポ (別サービス) であること — **他サービスへの興味がこの装置の主素材**。
   同一リポ内の 2 件は遠さの上限が低く、選ばれにくい。
2. Anatomia のドメインが異なること (`.anatomia/domains/*.json`)。ドメイン距離が
   取れない場合はリポが違えば遠いものとして扱う。
3. 最近その面で扱っていないこと (直近 N 日に散歩の素材にした組み合わせの種類を避ける)。

引き当てた 2 件に上下関係は付けない。どちらの制約をどちらに当てるかもランダムでよい。

## 2. 起動

- タイミングは **ポアソン過程**で、活動時間 1 日あたり平均 λ=2.5 回。等間隔にしない。
  λ は活動時間帯 (既定 10:00〜22:00 JST) の経過時間に対して適用する。次の発火が
  活動時間帯の外へ掛かる場合は捨てず、残りの待ち時間を次の活動時間帯へ繰り越す。
- delegation call は `CONCORDIA_CURIOSITY_CALL_NAME` で解決し、未設定時の既定は
  `claude-sonnet-5-walk`。options は `{ goal_and_go: false }`、1 ターンで終わる。
  設定キーと既定値は `setup/config-reference.md` にも記載する。
- workflow binding key は `curiosity` (単独で ON/OFF できる。**既定 OFF**。
  面が荒れる装置なので、有効化は人間の意思で行う)。
- このセッションの prompt と harness は読み取り専用を強制する。リポジトリのファイル編集 /
  commit / push / PR / テスト / サービス制御 / 追加 delegation を拒否する。読む対象は
  引き当てた 2 件の素材と、それらの要約に必要な spec に限る。

## 3. 出力

**1 投稿だけ**。既定の宛先は「ぼやき」チャンネル
([boyaki-channel.md](boyaki-channel.md))、無ければ chitchat。

- **`discord_pending_questions` を使わない**。カード化しない、催促しない、回答を待たない。
  direction 面と質問カードは本物のお伺いのための面であり、外れの多い装置を混ぜると
  お伺いの信号が薄まる。これは本 spec の成立条件である。
- 本文の型 (指示テンプレートで固定する):
  1. 引いた 2 件を 1 行ずつ (サービス名 + 何をしているか)。
  2. 移す制約を 1 つ名指しする (「A の X という縛りを B に当てると」)。
  3. その結果どうなるかを 3 行以内。**要否の結論は書かない**。
  4. 人間への問いを 1 つだけ。答えなくてよいと明記する。
- 実装・タスク化・PR は行わない。人間が拾ったときに初めて次が始まる。

## 4. 学習と減衰

- 投稿には `walk_id` を持たせ、`(repo_a, repo_b, domain_a, domain_b)` を記録する。
- **無回答・無反応が続いた組み合わせの種類は出現率を下げる**。個々の外れは罰しない
  (外れは仕様)。落とすのは種類の重みだけ。
- 反応 (リアクション / 返信 / その投稿を引用した spec・task・PR) があった種類は重みを上げる。

## 5. 効果測定

「発明できたか」は測れない。測るのは 1 つだけ。

- **その投稿が後で spec / spec/tasks / local PR から参照されたか** (`walk_id` を含む
  引用、または人間が手で貼ったリンク)。
- 参照率と 1 投稿あたりのコストを cost-observability に載せる。参照が 0 のまま
  一定期間 (既定 30 日) 続いたら、装置を止める判断材料として提示する
  (自動では止めない)。

## 6. 非対象

- 決定の取得 (`inquiry` の持ち場)。
- 自動でのタスク化・実装・PR 作成。
- direction 面 / 質問カード / 催促タイマーの使用。
- Cc 側での本文生成 (原則どおり行わない。生成は delegation 先のセッション)。

## 7. 受け入れ基準

- [ ] `curiosity` toggle が OFF の間、スケジューラも購読も登録されない (既定 OFF)。
- [ ] ON にすると活動時間帯の経過時間に対するポアソン間隔に起動し、等間隔にならない。
- [ ] 引き当てた 2 件が既定で別リポになる (同一リポの組は低確率でしか出ない)。
- [ ] 出力が 1 投稿だけで、`discord_pending_questions` を作らない。
- [ ] 散歩セッションから編集・commit・テスト・サービス制御が拒否される。
- [ ] 無反応が続いた組み合わせの種類の重みが下がる。
- [ ] `walk_id` の参照率がコスト面に出る。
