# デイリーゴール自走 (WM-2)

価値: UX-CC-W9 (主)、UX-CC-W2/W3/W4。シナリオ UX-CC-S10。
方式一覧での位置づけは [work-modes](work-modes.md)。

## 何をするか

人間がデイリーゴール用のチャンネルにその日の目標を投稿する。Cc は投稿からゴール文と受入条件を読み取り、
そろっていればゴールとして登録して専用セッションを起動する。そのセッションがゴールへ進み続け、人間は
1 時間ごとに届く確認カードを見て、判断が要るときだけ答える。翌朝 4:00 が締切で、Cc はその日にやったことを
まとめて Memoria の日記とノートへ記載する。
スクラムの計画・振り返りの儀式は持たない。日をまたぐ工程管理は WM-5 (Director 案件) に任せる。

### 経緯

- 2026-10-10 neco 指示 (初版): デイリーでゴールを決めて専用セッションを自走させ、1 時間おきに確認しながら
  Goal & Go する。止まるのはゴール到達・十分にこなした・人間の停止。
- 2026-10-10 neco 指示 (改訂): デイリーゴール用のチャンネルを作り、投稿でその日の目標を登録する形にする。
  ゴール / 受入条件が確認できない場合はその旨を知らせて定義してもらう。次の日の朝 4 時を締切として、
  4 時にその日やったことをまとめ、Memoria の日記とノートに記載する。目標がない場合は 9:00 に通知する。
  「目標なし」の日は許容する。7:30 の起動時刻は撤廃する。

改訂で撤廃したもの: 朝 7:30 の起動時刻 (`daily_goal.launch_time`)、朝の候補カード
(`daily_goal.candidate_projects`)、`/co-daily-goal` コマンド。登録の入口は投稿だけにする。

## 用語

- **その日 (業務日)**: 朝 4:00 から翌朝 4:00 まで。日付は始まりの 4:00 の日付 (ローカル時刻) で呼ぶ。
  10/11 の 2:00 の投稿は 10/10 の目標である。
- **デイリーゴールチャンネル**: Discord の「デイリーゴール」チャンネル。カテゴリを持たない (ルートに置き、カテゴリに入っていれば起動時に外へ出す。2026-10-10 neco 指示)。
  目標の投稿、聞き返し、確認カード、9:00 の通知、4:00 のまとめをここに置く。
- **デイリーゴール**: その日のうちに達成する成果。プロジェクト、ゴール文、受入条件、許可範囲を持ち、
  対応する Actio task を参照してよい。
- **下書き**: 投稿から読み取ったが、ゴール文・受入条件・プロジェクトのどれかが欠けているもの。
  欠けが埋まるまでゴールではない。
- **目標なし**: その日は目標を置かないという人間の宣言。正当な状態であり、催促しない。
- **専用セッション**: デイリーゴール 1 件に対して起動する 1 本のセッション。
- **確認 (checkpoint)**: 1 時間ごとに Cc が行う進み具合の確認。
- **証跡**: Cc が機械的に集めた進捗の根拠 (commit、PR とその状態、Actio task の状態変化)。
  セッション自身の自己申告は証跡に数えない。
- **許可範囲**: その日のうちに AI が実行してよい操作 (マージ・テスト・サービス操作・反映)。
  目標の投稿に人間が明示したものだけ。
- **日のまとめ**: 締切の 4:00 に Cc が作る、その日のゴールごとの結果・証跡・残りの記録。

## 状態の所有者

| 状態 | 所有者 | 備考 |
|---|---|---|
| タスクの内容・状態 | Actio | 進捗の正本。Cc は task ID を参照するだけで書き換えない |
| デイリーゴール・下書き・目標なし (ゴール文・受入条件・許可範囲・投稿者・元投稿) | Cc `daily-goal-run` | 投稿した人の Discord 上の本人性と元投稿の message id を保存する |
| 専用セッションとの紐付け、確認の記録、停止理由、日のまとめと記載の状態 | Cc `daily-goal-run` | |
| セッション内の自走継続 | Cc `autonomous-continuation` (Goal & Go) | 予算の扱いは下記「予算」 |
| 起動の実体 | Cc `agent-delegation` | 専用テンプレートで spawn する |
| 日記の本文・ノートの本文 | Memoria (`memo-and-diary`) と Tabula | Cc は日のまとめを渡すだけで、日記の他の欄やノートの他の内容を書き換えない |

## 流れ

### 1. 目標を投稿する

- 人間がデイリーゴールチャンネルに、その日の目標を自由文で投稿する。1 投稿 = 1 ゴール。
  1 日に複数のゴールを投稿してよい (ゴールごとに専用セッションが 1 本)。
- 書いてほしいこと (チャンネルの説明と 9:00 の通知に載せる):
  - プロジェクト (略称でもフルネームでもよい)
  - ゴール (その日に達成すること)
  - 受入条件 (確認で照合できる形。例: 「PR がマージされ、Cc で反映を確認」)
  - 任意: 許可 (マージ / テスト / サービス操作 / 反映 のうち許すもの)、Actio task ID
- 本文が「目標なし」(前後の空白・句読点を除いて一致) の投稿は、その日の **目標なし** として記録する。
- bot・webhook・system の投稿、スレッド内の投稿、Cc 自身の投稿は登録に使わない。
  ただし聞き返しのスレッドでの元投稿者の返信は、その下書きの補足として読む (下記 2)。

### 2. ゴール・受入条件を読み取り、欠けていれば定義してもらう

Cc は投稿本文からプロジェクト・ゴール文・受入条件・許可・Actio task ID を読み取る。

- 読み取りは **投稿に書かれていることだけ** を拾う。書かれていない受入条件をゴール文から推測して作らない。
  読み取りに LLM を使う場合も、各項目は本文からの引用 (または本文の言い換えであることが確認できるもの) に限る。
- 次のどれかが欠けている、または一意に決まらないときは登録せず **下書き** にする:
  - プロジェクト (Cc の project registry で一意に解決できない)
  - ゴール文
  - 受入条件 (1 件以上)
- 下書きにしたら、元投稿へのスレッドで「何が読み取れて、何が足りないか」を返し、定義を頼む。
  返信の例: 「ゴールは『◯◯』と読み取りました。受入条件が見つかりません。何がそろったら達成としますか?」
- 元投稿者がそのスレッドで返信するか元投稿を編集したら、元投稿と返信を合わせて読み直す。
  そろったら登録し、そろわなければ足りない項目だけを聞き直す。聞き返しは 1 回の読み直しにつき 1 通。
- 許可は本文に明示されたものだけを可にし、書かれていなければすべて不可。
  `merge`・`deploy` を可にするには投稿者に `merge_pr` (manager 以上)、登録そのものには
  `session_spawn` (staff 以上) が要る。権限を超える許可は不可に落とし、そのことをスレッドで知らせる。
  権限が足りず登録できない投稿者にはその旨を返す。
- 読み取りの結果 (プロジェクト・ゴール文・受入条件・許可) は登録時にスレッドへ返す。読み違いは人間が
  停止して投稿し直す (登録済みゴールの書き換えはしない)。

### 3. 専用セッションを起動する

- 登録したら **その場で** 起動する。起動時刻の制限は持たない (7:30 は撤廃)。
- 締切 (4:00) の前 30 分以内に登録したゴールも起動するが、カードに締切が近いことを出す。
- 起動は `agent-delegation` の専用テンプレート `daily-goal-runner` を使う。
  依頼文にはゴール文・受入条件・許可範囲・Actio task ID・締切時刻だけを入れる。
- 同じデイリーゴールに対する起動は 1 回だけ。依頼の同一性は起動前に保存した run id で持つ。
  起動の結果が不明なときは既存の run とセッションを照合し、見つからない間は再起動しない (CC-INV-03)。
  同じ投稿 (message id) から 2 件目のゴールを作らない。
- 作業場所はプロジェクトの規則 (task worktree / direct-main) に従う。

### 4. 確認と確認の間 — Goal & Go で自走

- 専用セッションは Goal & Go が ON。明示ゴールとしてデイリーゴールを渡す。
- セッションはゴールの範囲だけで作業する。Actio の他の未着手 task や git diff の残りを持ち込まない
  (goal-and-go の 2026-10-07 の不変条件と同じ)。
- 許可範囲に無い操作が必要になったら、ask で聞いて止まる。

### 5. 1 時間ごとの確認

Cc が 1 時間ごとに次を行う。

1. 証跡を集める: 前回の確認以降の commit、PR の提出・審査・マージ、Actio task の状態変化。
2. セッションへ確認の inject を送り、受入条件に対する進み具合・次の 1 時間でやること・
   人間判断が要る点を、決まった形で書かせる。
3. デイリーゴールのカード (デイリーゴールチャンネルに 1 ゴール 1 枚) を同じ message の更新で書き換え、
   タイムラインに 1 行足す。カードには 証跡 / セッションの報告 / 人間判断 を分けて載せる。
4. 進捗を判定する。前回から証跡が 1 件以上増えていれば「進捗あり」、増えていなければ「進捗なし」。
5. **進捗なしでも止めない。** 確認の inject を「完了確認」に切り替え、受入条件と対応する Actio task の
   一つずつについて、完了しているか・残りは何かをセッションに確かめさせる。
   - すべて完了している → 6 の「ゴール到達」の照合へ進む。
   - AI だけで進められる残りがある → その残りを次の 1 時間でやることとして書かせ、続行 (GO) する。
   - 残りがすべて達成不能か人間判断待ち → 6 の「十分にこなした」の照合へ進む。

回答待ちの扱い:

- 未回答の質問があるセッションには確認の inject を送らない (CC-INV-08)。
  カードには「回答待ち」と経過時間だけを出し、催促は 1 回にとどめる。
- 回答待ちの間は予算を消費しない。回答が付いたら次の確認から通常どおり続ける。

### 6. 終わり方

止まる条件は次の 4 つだけ。進捗の停滞では止めない。

| 止まる条件 | 照合 | カード |
|---|---|---|
| **ゴールに到達した** | 受入条件の一つずつに対応する証跡 (PR のマージ、反映の確認、Actio task の完了など) がそろっている。セッションの「終わった」だけでは到達にしない | 「達成」 |
| **十分にタスクをこなした** | セッションが残りの一覧を出し、残りの一つずつが「達成不能 (理由付き)」か「人間判断待ち (未回答の質問・人間依頼に対応)」のどちらかである。AI だけで進められる残りが 1 件でもあれば認めず、続行 (GO) を返す | 「やり切り」。残りの一覧と、人間に決めてほしい点を載せる |
| **人間が停止した** | 人間本人の停止操作 (カードの停止ボタン) | 「停止」 |
| **締切 (翌朝 4:00) に達した** | その日のゴールでまだ走っているもの。締切の直前に最後の証跡を集め、受入条件ごとの到達状況を記録してから止める | 「締切」。到達した受入条件と残りを載せる |

止まる条件ではないが、状態として扱うもの:

| 状態 | 動作 |
|---|---|
| セッションの喪失 | 「喪失」と表示し、自動で別セッションを起動しない。再開は人間が選ぶ (UX-CC-S3)。日のまとめには喪失として載せる |
| 0:00 (日付の変わり目) | 止めない。その日の締切は翌朝 4:00 |

終了は既存の session-end 手順に合流する。「やり切り」「締切」の残りは日のまとめに載せるが、
翌日のゴールには自動でならない。

### 7. 9:00 の通知

- その日の 9:00 (業務日の始まりから 5 時間後) に、その日のゴール・下書き・目標なしが 1 件も無ければ、
  デイリーゴールチャンネルへ通知を 1 回出す。通知には投稿の書き方と、「目標なし」で済ませてよいことを載せる。
- 目標なしが記録された日、ゴールか下書きがある日は通知しない。9:00 より後に通知を繰り返さない。
- 通知の intent を先に保存し、結果不明で同じ通知を再送しない。

### 8. 4:00 の締切と日のまとめ

翌朝 4:00 に、その日 (業務日) について次を順に行う。

1. まだ走っているゴールを「締切」で止める (6 の表)。
2. 日のまとめを作る。ゴールごとに: プロジェクト、ゴール文、結果 (達成 / やり切り / 停止 / 締切 / 喪失)、
   受入条件ごとの到達と証跡 (PR・commit・Actio task)、セッションの最後の報告、残りと人間に決めてほしい点。
   日全体として: ゴール数と結果の内訳、マージされた PR の一覧。
   まとめは Cc が集めた証跡と確認記録から組み立てる。セッションの自己申告は「報告」として区別して載せる。
3. Memoria へ記載する。
   - **日記**: その日の日付の日記に「デイリーゴール」節として書く。日記の他の欄 (サマリ・作業内容・
     ユーザメモ) は書き換えない。同じ日の節は上書き (再実行しても 1 つ)。
   - **ノート**: 「デイリーゴール YYYY-MM-DD」というノートを 1 本作る。同じ日のノートは 1 本だけ
     (外部 ID `concordia-daily-goal:YYYY-MM-DD` で重複を防ぐ)。
   - 記載の intent を先に保存し、結果不明のときは外部 ID で照合してから再送する。Memoria に届かないときは
     「未記載」として残し、次の tick で再送する。人間が手で再送する操作も用意する。
4. デイリーゴールチャンネルにまとめの要約と、日記・ノートへのリンクを投稿する。
- **目標なし** の日、ゴールが 1 件も無い日は、日記・ノートへ記載しない。チャンネルへの投稿もしない。
- 下書きのまま締切を迎えたものは、ゴールにせず「未定義のまま締切」としてまとめに載せる
  (ゴールが 1 件も無く下書きだけの日は、下書きの一覧だけを日記に書く)。

## 予算

- 時刻による上限は締切 (4:00) だけ。それ以外に止まるのは上記の条件だけ。
- 確認と確認の間は、Goal & Go の既存の上限 (人間入力 1 回あたり 6 回・2 時間) をそのまま使う。
- **緩和は 1 つだけ**: 1 時間ごとの確認 (進捗あり、または完了確認で AI だけで進められる残りが
  ある場合) を、Goal & Go の継続回数と時間の予算のリセットとして扱う。人間の目標の投稿が
  止まる条件までの続行を許可しているため。回答待ちと、止まる条件に当たった後はリセットしない
  (CC-WM-INV-03 で許す唯一の緩和)。
- 委託 run の起動回数は既存の delegation の上限に従い、緩和しない。

## 他の方式との違い

- **WM-1 対話**: 対話は人間の指示ごとに自走予算が戻る。デイリーゴールは投稿 1 回で止まる条件まで進み、
  予算は 1 時間ごとの確認で戻る。
- **WM-5 Director 案件**: 案件は日をまたぎ、分解と委託を工程として追う。デイリーゴールはゴール 1 件に 1 セッションで、
  分解はセッション自身が行う。複数日の仕事は案件にし、その日の分をデイリーゴールとして切り出してよい。
- **WM-7 スプリント (休止)**: 計画・振り返りの会合とフェーズ遷移を持たない。1 日の投稿と 1 時間の確認と 4:00 のまとめだけ。

## Memoria との契約

Memoria 側の正本は Memoria の `spec/feature/diary.md` (日記の外部節) と、ノートの取り込み口の仕様。
Cc は loopback で次を呼ぶ。接続先は Cc のサービス URL 設定 (`memoria`) から解決する。

| メソッド | パス | body | 意味 |
|---|---|---|---|
| PUT | `/api/diary/:date/sections/:source` | `{ title, markdown }` | 日記のその日の外部節を置き換える。`source` は `concordia-daily-goal`。日記の他の欄は変えない |
| GET | `/api/diary/:date/sections/:source` | — | 記載済みかの照合 |
| POST | `/api/notes/from-text` | `{ external_id, title, markdown, source }` | ノートを 1 本作る。同じ `external_id` なら作らずに既存を返す |

## 実装

### 初版 (2026-10-10)

次の 5 単位を 1 PR にまとめて実装した (neco 指示「実装開始」)。設計判断の正本は
`spec/tasks/2026-10-10-daily-goal-run-impl.md`。

1. ドメイン `src/daily-goal-run/`: 判断は `confirmation-policy` / `launch-policy` / `checkpoint-policy` /
   `stop-policy` の純関数、手順は `service` (確定) ・`launch` ・`checkpoint` ・`finish` ・`candidates` の use case、
   保存は `repository` (`daily_goals` / `daily_goal_checkpoints` / `daily_goal_timeline` / `daily_goal_cards` /
   `daily_goal_candidates`)、外部 I/O は `ports` と `evidence` (git / pr_records / Revisor / Actio の読み取り)。
2. 起動: delegation テンプレート `daily-goal-runner` (call_only、Opus 5.5 / medium)。依頼の同一性は
   起動前に保存した run id (`reserved_run_id`) で持ち、結果不明は run 台帳と照合する。Actio に新しい task を
   封印しない (`task_binding: "caller"`)。
3. 確認: `scheduler` が 1 分ごとに tick し、起動・照合・確認・候補を進める。Goal & Go の予算は
   `resetGoalAndGoBudget` (`src/control/goal-and-go.ts`) で戻す。呼ぶのは進捗ありの確認と、完了確認への
   doable 返答だけ。
4. 表示: Discord の「デイリーゴール」チャンネル (カテゴリなし) にゴールごと 1 枚のカードを置き、
   同じ message を編集する。停止ボタンと候補の確定モーダル、`/co-daily-goal`。
5. 方式の記録: `src/work-modes/work-mode.ts` (`work_mode` metadata、CC-WM-INV-01)。

### HTTP (loopback 限定、workflow `daily_goal` が無効なら 409)

| メソッド | パス | 呼べる主体 |
|---|---|---|
| GET | `/v1/daily-goals?date=YYYY-MM-DD` | 読み取り |
| GET | `/v1/daily-goals/:id` (確認記録・タイムライン込み) | 読み取り |
| GET | `/v1/daily-goals/days/:date` (目標なし・通知・まとめ・記載の状態) | 読み取り |
| POST | `/v1/daily-goals/:id/reached` `{session_id, evidence:[{item, refs[]}], report?}` | 紐付いた専用セッションだけ |
| POST | `/v1/daily-goals/:id/exhausted` `{session_id, remaining:[…], report?}` | 紐付いた専用セッションだけ |
| POST | `/v1/daily-goals/:id/report` `{session_id, report}` | 紐付いた専用セッションだけ |

登録と停止の HTTP は設けない (人間の判断は Discord の本人操作だけ)。証跡の参照 (`refs`) は
`commit:<sha>` / `pr:<origin>#<n>:<state>` / `revisor:<id>:<status>:<check>` / `actio:<id>:done` の形で、
Cc が集めた証跡に実在するものだけを到達の照合に使う。`report` はセッションの自己申告としてカードに
載せるだけで、進捗・到達の判定には使わない (CC-DG-INV-03)。
まとめの手動再送は Discord のまとめ投稿のボタン (本人確認 + `session_control`) で行う。

### 設定 (設定 > ワークフロー)

- `daily_goal.checkpoint_minutes` (既定 60): 確認の間隔。
- `daily_goal.day_boundary` (既定 `04:00`): 業務日の境界 = 締切。
- `daily_goal.reminder_time` (既定 `09:00`): 目標が無い日の通知時刻。
- workflow toggle `daily_goal` (既定 有効): 無効の間は scheduler・投稿の読み取り・API・カードの操作を止める。
- 撤廃: `daily_goal.launch_time`、`daily_goal.candidate_projects`。

### 既知の制約

- 「反映を Ex で確認」のような Cc が機械的に集められない受入条件は、到達の証跡にならない。
  そうした条件は「人間判断待ち」として「やり切り」で報告し、人間がカードで確かめる。
- 日記・ノートは Memoria のある本社の端末だけに書く。Memoria が止まっている間は「未記載」で残る。

## 受け入れ基準

- [ ] デイリーゴールチャンネルへの人間の投稿から、ゴール文・受入条件・プロジェクトがそろえばその場で専用セッションが起動する。
- [ ] ゴール文・受入条件・プロジェクトのどれかが読み取れない投稿は登録せず、足りない項目をスレッドで返す。返信・編集で埋まれば登録する。
- [ ] 本文に無い受入条件を作らない。許可は本文に明示され、投稿者の権限で認められたものだけ。
- [ ] 同じゴールで 2 本目が起動せず、同じ投稿から 2 件目のゴールが作られない。
- [ ] 1 時間ごとに証跡・報告・判断点が同じカードの更新で届く。
- [ ] 1 時間ごとの確認で Goal & Go の予算が戻り、回答待ちと停止後は戻らない。
- [ ] 進捗なしの確認では完了確認を送り、AI だけで進められる残りがあれば続行する。
- [ ] ゴール到達・十分にこなした・人間の停止・締切の 4 つでだけ止まり、停滞では止まらない。0:00 では止まらない。
- [ ] 「十分にこなした」は、AI だけで進められる残りが 1 件でもあれば認めない。
- [ ] 回答待ちの間は確認と自走を送らず、予算を消費しない。
- [ ] 許可範囲に無い操作をセッションが行わず、聞いて止まる。
- [ ] 4:00 に走っているゴールが締切で止まり、日のまとめが Memoria の日記 (節 1 つ) とノート (1 本) に記載される。再実行しても増えない。
- [ ] 目標なしの日は記載せず、9:00 の通知も出さない。
- [ ] ゴール・下書き・目標なしが無い日は 9:00 に通知が 1 回だけ出る。
- [ ] 7:30 の起動時刻、候補カード、`/co-daily-goal` が無い。
