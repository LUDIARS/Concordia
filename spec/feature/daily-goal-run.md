# デイリーゴール (WM-2)

価値: UX-CC-W9 (主)、UX-CC-W2/W3/W4。シナリオ UX-CC-S10。
方式一覧での位置づけは [work-modes](work-modes.md)。

## 何をするか

人間がデイリーゴール用のチャンネルにその日の目標を投稿する。Cc は投稿からゴール文と受入条件を読み取り、
そろっていればゴールとして登録する。作業そのものは人間が自分の選んだ方法 (対話・委託など) で進める。
Cc は 1 時間ごとに進み具合をワンショットで判定してカードを更新し、進捗が芳しくないときだけ投稿者に知らせる。
翌朝 4:00 が締切で、Cc はその日にやったことをまとめて Memoria の日記とノートへ記載する。
スクラムの計画・振り返りの儀式は持たない。日をまたぐ工程管理は WM-5 (Director 案件) に任せる。

## 用語

- **その日 (業務日)**: 朝 4:00 から翌朝 4:00 まで。日付は始まりの 4:00 の日付 (ローカル時刻) で呼ぶ。
  10/11 の 2:00 の投稿は 10/10 の目標である。
- **デイリーゴールチャンネル**: Discord の「デイリーゴール」チャンネル。カテゴリを持たない (ルートに置き、カテゴリに入っていれば起動時に外へ出す。2026-10-10 neco 指示)。
  目標の投稿、聞き返し、カード、不調の通知、9:00 の通知、4:00 のまとめをここに置く。
- **デイリーゴール**: その日のうちに達成する成果。プロジェクト、ゴール文、受入条件、許可範囲を持ち、
  対応する Actio task を参照してよい。
- **ゴールのスレッド**: 登録元の投稿に付いたスレッド (読み取り結果と聞き返しを返したもの)。
- **下書き**: 投稿から読み取ったが、ゴール文・受入条件・プロジェクトのどれかが欠けているもの。
  欠けが埋まるまでゴールではない。
- **目標なし**: その日は目標を置かないという人間の宣言。正当な状態であり、催促しない。
- **確認 (checkpoint)**: 1 時間ごとに Cc が行う進み具合の確認。証跡の収集と判定の 1 組。
- **証跡**: Cc が機械的に集めた進捗の根拠 (commit、PR とその状態、Actio task の状態変化)。
  人の自己申告は証跡に数えない。
- **判定**: 確認のたびに 1 回だけ行う、セッションを残さない LLM 呼び出しの結果。
  「順調 / 遅れ気味 / 停滞」、受入条件ごとの到達見込み (到達 / 見込みあり / 危うい / 見込みなし)、一言の理由。
  失敗・時間切れは「判定できず」。
- **不調**: 判定が「遅れ気味」か「停滞」であること。「順調」に戻るまでを 1 続きの不調とする。
- **許可範囲**: その日のうちに AI が実行してよい操作 (マージ・テスト・サービス操作・反映)。
  目標の投稿に人間が明示したものだけ。作業する人・セッションへの申し送りとしてカードに載せる。
- **日のまとめ**: 締切の 4:00 に Cc が作る、その日のゴールごとの結果・証跡・最後の判定・残りの記録。

## 状態の所有者

| 状態 | 所有者 | 備考 |
|---|---|---|
| タスクの内容・状態 | Actio | 進捗の正本。Cc は task ID を参照するだけで書き換えない |
| デイリーゴール・下書き・目標なし (ゴール文・受入条件・許可範囲・投稿者・元投稿) | Cc `daily-goal-run` | 投稿した人の Discord 上の本人性と元投稿の message id を保存する |
| 確認と判定の記録、不調の通知の記録、停止理由、日のまとめと記載の状態 | Cc `daily-goal-run` | |
| 判定の実行 | Cc `daily-goal-run` (既存の headless 実行 `runClaude`、会話のみ) | セッションを作らない |
| 日記の本文・ノートの本文 | Memoria (`memo-and-diary`) と Tabula | Cc は日のまとめを渡すだけで、日記の他の欄やノートの他の内容を書き換えない |

## 流れ

### 1. 目標を投稿する

- 人間がデイリーゴールチャンネルに、その日の目標を自由文で投稿する。1 投稿 = 1 ゴール。
  1 日に複数のゴールを投稿してよい。
- 書いてほしいこと (チャンネルの説明と 9:00 の通知に載せる):
  - プロジェクト (略称でもフルネームでもよい)
  - ゴール (その日に達成すること)
  - 受入条件 (確認で照合できる形。例: 「PR がマージされ、Cc で反映を確認」)
  - 任意: 許可 (マージ / テスト / サービス操作 / 反映 のうち許すもの)、Actio task ID
- 本文が「目標なし」(前後の空白・句読点を除いて一致) の投稿は、その日の **目標なし** として記録する。
- bot・webhook・system の投稿、スレッド内の投稿、Cc 自身の投稿は登録に使わない。
  ただし聞き返しのスレッドでの元投稿者の返信は、その下書きの補足として読む (下記 2)。

### 2. ゴール・受入条件を読み取り、欠けていれば定義してもらう

Cc は投稿本文からプロジェクト・ゴール文・受入条件・許可・Actio task ID を読み取る。

- 読み取りは **投稿に書かれていることだけ** を拾う。書かれていない受入条件をゴール文から推測して作らない。
  読み取りに LLM を使う場合も、各項目は本文からの引用 (または本文の言い換えであることが確認できるもの) に限る。
- 次のどれかが欠けている、または一意に決まらないときは登録せず **下書き** にする:
  - プロジェクト (Cc の project registry で一意に解決できない)
  - ゴール文
  - 受入条件 (1 件以上)
- 下書きにしたら、元投稿へのスレッドで「何が読み取れて、何が足りないか」を返し、定義を頼む。
  返信の例: 「ゴールは『◯◯』と読み取りました。受入条件が見つかりません。何がそろったら達成としますか?」
- 元投稿者がそのスレッドで返信するか元投稿を編集したら、元投稿と返信を合わせて読み直す。
  そろったら登録し、そろわなければ足りない項目だけを聞き直す。聞き返しは 1 回の読み直しにつき 1 通。
- 許可は本文に明示されたものだけを可にし、書かれていなければすべて不可。
  `merge`・`deploy` を可にするには投稿者に `merge_pr` (manager 以上)、登録そのものには
  `session_spawn` (staff 以上) が要る。権限を超える許可は不可に落とし、そのことをスレッドで知らせる。
  権限が足りず登録できない投稿者にはその旨を返す。
- 読み取りの結果 (プロジェクト・ゴール文・受入条件・許可) は登録時にスレッドへ返す。読み違いは人間が
  停止して投稿し直す (登録済みゴールの書き換えはしない)。

### 3. 登録 — セッションは起動しない

- 登録したゴールはその場で「見守り中」(`running`) になる。Cc はセッションを起動しない。
  作業は人間が自分の選んだ方法 (対話・委託など) で進める。
- 締切 (4:00) の前 30 分以内に登録したゴールも登録し、カードに締切が近いことを出す。
- 同じ投稿 (message id) から 2 件目のゴールを作らない。
- 2026-10-14 より前に旧方式で起動した専用セッションには触らない (自動で止めない・inject しない)。
  そのゴールも以後は新方式の確認だけを受ける。

### 4. 1 時間ごとのワンショット確認

Cc が見守り中のゴールごとに、前回の確認 (無ければ登録) から `daily_goal.checkpoint_minutes` (既定 60 分)
ごとに次を行う。

1. **証跡を集める**: 登録以降の commit、PR の提出・審査・マージ、Actio task の状態変化。
   - commit はゴールのプロジェクトの repo のローカル branch 全体 (`git log --branches`) から取る。
     旧方式で専用セッションが紐付いたゴールは、そのセッションの branch を ref 名として検証してから取る。
     先頭 `-` などの不正値では Git を呼ばず `unavailable` に `git` を残す。有効な revision は `--end-of-options` の直後へ置く。
   - PR は Cc の pr_records (プロジェクトの repo origin) と Revisor local PR (同じ repository) から、登録以降に更新されたものを取る。
   - Actio task は読み取りだけ。読めなかった情報源は `unavailable` に残し、空の成功にしない。
2. **1 回限りの判定**: セッションを残さない headless 実行 (`runClaude`、会話のみ・ツールなし) を 1 回呼ぶ。
   - 材料はゴール文・受入条件・証跡・経過時間 (登録から)・締切までの残り時間だけ。
   - ゴール文と受入条件は投稿本文由来の「目標」として、証跡 (commit の件名・PR の題名など人や AI が書いた文) は
     「資料」として区切って渡し、資料の中の指示には従わないよう明記する。投稿本文以外の人の文を指示として混ぜない。
   - 返させるもの: 「順調 / 遅れ気味 / 停滞」、受入条件ごとの到達見込みと根拠の証跡キー、一言の理由。
   - 返った値は信用しない。根拠の証跡キーは Cc が集めた証跡に実在するものだけを残す。形が違えば「判定できず」。
3. **ゴール到達の照合**: 判定が受入条件の全項目を「到達」とし、かつ全項目に実在する証跡キーが 1 件以上あれば
   「達成」で止める (6)。判定の「到達」だけで証跡が無い項目は到達にしない。
4. **カードを更新する**: 証跡と判定 (順調/遅れ気味/停滞・理由・受入条件ごとの見込み) を同じ message の更新で書き換え、
   タイムラインに 1 行足す。
5. **不調なら人間に知らせる** (5)。順調ならカードの更新だけで通知しない。
6. **判定できず** (headless の失敗・時間切れ・解釈できない出力) は「判定できず」としてカードに出し、通知はしない。
   不調の続き具合も変えない。次の確認でまた試す。

### 5. 不調の通知

- 判定が「遅れ気味」か「停滞」のとき、そのゴールのスレッド (無ければカードへの返信) に投稿者を mention して知らせる。
  文面は状態・理由・危うい受入条件と、カードへの案内だけ。
- mention は構造化フィールド (`allowedMentions.users` に投稿者 1 人) で行う。判定文由来の mention・`@everyone`・
  ロール mention は発火させない。
- 1 続きの不調への通知は最初の 1 回だけ。不調が 3 時間続いたら 1 回だけ再通知し、それ以後は重ねない。
  「順調」に戻ったら続き具合を戻し、次の不調でまた最初から数える。
- 通知は intent を先に保存してから送る。結果不明は再送しない (CC-INV-03)。

### 6. 終わり方

止まる条件は次の 3 つだけ。不調では止めない。

| 止まる条件 | 照合 | カード |
|---|---|---|
| **ゴールに到達した** | 受入条件の一つずつに、Cc が集めた証跡のうち判定が根拠に挙げた実在のもの (PR のマージ、Actio task の完了など) がある | 「達成」 |
| **人間が停止した** | 人間本人の停止操作 (カードの停止ボタン) | 「停止」 |
| **締切 (翌朝 4:00) に達した** | その日のゴールでまだ見守り中のもの。締切の直前に最後の証跡を集め、受入条件ごとの到達状況を記録してから止める | 「締切」。到達した受入条件と残りを載せる |

- 0:00 (日付の変わり目) では止めない。その日の締切は翌朝 4:00。
- 「締切」の残りは日のまとめに載せるが、翌日のゴールには自動でならない。
- 旧方式で記録された「やり切り」「喪失」は履歴として表示・まとめに残す (新たには作らない)。

### 7. 9:00 の通知

- その日の 9:00 (業務日の始まりから 5 時間後) に、その日のゴール・下書き・目標なしが 1 件も無ければ、
  デイリーゴールチャンネルへ通知を 1 回出す。通知には投稿の書き方と、「目標なし」で済ませてよいことを載せる。
- 目標なしが記録された日、ゴールか下書きがある日は通知しない。9:00 より後に通知を繰り返さない。
- 通知の intent を先に保存し、結果不明で同じ通知を再送しない。

### 8. 4:00 の締切と日のまとめ

翌朝 4:00 に、その日 (業務日) について次を順に行う。

1. まだ見守り中のゴールを「締切」で止める (6 の表)。
2. 日のまとめを作る。ゴールごとに: プロジェクト、ゴール文、結果 (達成 / 停止 / 締切、旧方式の やり切り / 喪失)、
   受入条件ごとの到達と証跡 (PR・commit・Actio task)、最後の判定 (状態・理由)、残り。
   日全体として: ゴール数と結果の内訳、マージされた PR の一覧。
   まとめは Cc が集めた証跡と確認記録から組み立てる。判定は「最後の判定」として証跡と区別して載せる。
3. Memoria へ記載する。
   - **日記**: その日の日付の日記に「デイリーゴール」節として書く。日記の他の欄 (サマリ・作業内容・
     ユーザメモ) は書き換えない。同じ日の節は上書き (再実行しても 1 つ)。
   - **ノート**: 「デイリーゴール YYYY-MM-DD」というノートを 1 本作る。同じ日のノートは 1 本だけ
     (外部 ID `concordia-daily-goal:YYYY-MM-DD` で重複を防ぐ)。
   - 記載の intent を先に保存し、結果不明のときは外部 ID で照合してから再送する。Memoria に届かないときは
     「未記載」として残し、次の tick で再送する。人間が手で再送する操作も用意する。
4. デイリーゴールチャンネルにまとめの要約と、日記・ノートへのリンクを投稿する。
- **目標なし** の日、ゴールが 1 件も無い日は、日記・ノートへ記載しない。チャンネルへの投稿もしない。
- 下書きのまま締切を迎えたものは、ゴールにせず「未定義のまま締切」としてまとめに載せる
  (ゴールが 1 件も無く下書きだけの日は、下書きの一覧だけを日記に書く)。

## 予算

- 時刻による上限は締切 (4:00) だけ。
- 判定の呼び出しはゴール 1 件につき確認 1 回あたり 1 回 (既定で 1 時間に 1 回)。失敗しても同じ確認の中で再試行しない。
- セッションを起動しないので、Goal & Go と委託の予算には関わらない。Goal & Go の予算の緩和は持たない
  (CC-WM-INV-03 の緩和は 2026-10-14 に撤廃)。

| CC-DG-INV-09 | 受入条件を投稿本文から推測して作らない。欠けていれば登録せず、何が足りないかを投稿者に返す |
| CC-DG-INV-10 | 日のまとめは 1 業務日につき日記の節 1 つ・ノート 1 本。日記の他の欄とノートの他の内容を書き換えない。目標なしの日は記載しない |
| CC-DG-INV-11 | 9:00 の通知は、ゴール・下書き・目標なしが 1 件も無い日に 1 回だけ。目標なしの日を催促しない |
| CC-DG-INV-12 | 不調の通知は 1 続きの不調につき最初の 1 回と、3 時間続いたときの再通知 1 回まで。mention は投稿者 1 人を構造化フィールドで指定し、判定文由来の mention を発火させない。結果不明の通知を再送しない |

CC-INV-03/04/06、CC-WM-INV-01/02/04 を適用する。

## 他の方式との違い

- **WM-1 対話**: 作業は人間とセッションの対話で進む。デイリーゴールはその日の到達点を宣言し、Cc が 1 時間ごとに
  外から見て、芳しくなければ知らせるだけ。作業の進め方 (対話・委託) は問わない。
- **WM-5 Director 案件**: 案件は日をまたぎ、分解と委託を工程として追う。デイリーゴールは 1 日の到達点と見守りだけ。
  複数日の仕事は案件にし、その日の分をデイリーゴールとして切り出してよい。
- **WM-7 スプリント (休止)**: 計画・振り返りの会合とフェーズ遷移を持たない。1 日の投稿と 1 時間の確認と 4:00 のまとめだけ。

## Memoria との契約

Memoria 側の正本は Memoria の `spec/feature/diary.md` (日記の外部節) と、ノートの取り込み口の仕様。
Cc は loopback で次を呼ぶ。接続先は Cc のサービス URL 設定 (`memoria`) から解決する。

| メソッド | パス | body | 意味 |
|---|---|---|---|
| PUT | `/api/diary/:date/sections/:source` | `{ title, markdown }` | 日記のその日の外部節を置き換える。`source` は `concordia-daily-goal`。日記の他の欄は変えない |
| GET | `/api/diary/:date/sections/:source` | — | 記載済みかの照合 |
| POST | `/api/notes/from-text` | `{ external_id, title, markdown, source }` | ノートを 1 本作る。同じ `external_id` なら作らずに既存を返す |

### 設定 (設定 > ワークフロー)

- `daily_goal.checkpoint_minutes` (既定 60): 確認 (判定) の間隔。
- `daily_goal.day_boundary` (既定 `04:00`): 業務日の境界 = 締切。
- `daily_goal.reminder_time` (既定 `09:00`): 目標が無い日の通知時刻。
- workflow toggle `daily_goal` (既定 有効): 無効の間は scheduler・投稿の読み取り・API・カードと通知の配達を止める。

### 既知の制約

- 「反映を Ex で確認」のような Cc が機械的に集められない受入条件は、到達の証跡にならない。
  そうしたゴールは締切まで見守り中のままで、人間がカードで確かめて停止する。
- commit 証跡はプロジェクトの repo のローカル branch 全体から取るため、そのゴールと関係の無い同じ repo の commit も
  資料に入る。関係の判断は判定に任せ、到達の照合は判定が受入条件ごとに挙げた実在の証跡キーで行う。
- 日記・ノートは Memoria のある本社の端末だけに書く。Memoria が止まっている間は「未記載」で残る。

## 受け入れ基準

- [ ] デイリーゴールチャンネルへの人間の投稿から、ゴール文・受入条件・プロジェクトがそろえば登録される。セッションは起動しない。
- [ ] ゴール文・受入条件・プロジェクトのどれかが読み取れない投稿は登録せず、足りない項目をスレッドで返す。返信・編集で埋まれば登録する。
- [ ] 本文に無い受入条件を作らない。許可は本文に明示され、投稿者の権限で認められたものだけ。
- [ ] 同じ投稿から 2 件目のゴールが作られない。
- [ ] 1 時間ごとに証跡を集めて判定を 1 回だけ呼び、証跡・判定 (状態・理由・受入条件ごとの見込み) が同じカードの更新で届く。
- [ ] 判定の入力はゴール文・受入条件・証跡・経過時間・締切までの残り時間だけで、証跡は資料として区切られている。
- [ ] 「遅れ気味」「停滞」のときだけ、ゴールのスレッド (無ければカード) に投稿者 1 人への mention で通知する。判定文由来の mention は発火しない。
- [ ] 1 続きの不調への通知は 1 回で、3 時間続いたら 1 回だけ再通知する。「順調」に戻れば次の不調でまた通知する。
- [ ] 判定の失敗・時間切れは「判定できず」としてカードに出し、通知せず、次の確認でまた試す。
- [ ] 受入条件の全項目に判定が挙げた実在の証跡があれば「達成」で止まる。証跡の無い「到達」では止まらない。
- [ ] ゴール到達・人間の停止・締切の 3 つでだけ止まり、不調では止まらない。0:00 では止まらない。
- [ ] 4:00 に見守り中のゴールが締切で止まり、日のまとめ (最後の判定を含む) が Memoria の日記 (節 1 つ) とノート (1 本) に記載される。再実行しても増えない。
- [ ] 目標なしの日は記載せず、9:00 の通知も出さない。
- [ ] ゴール・下書き・目標なしが無い日は 9:00 に通知が 1 回だけ出る。
- [ ] `daily-goal-runner` テンプレートが seed に無く、既存 DB の定義行も消える。旧方式の走行中セッションは自動で止めない。
