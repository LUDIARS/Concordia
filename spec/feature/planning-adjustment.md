# 企画調整課

2026-10-02 neco の「Ludellus のプランナーが非エンジニアでも調整可能な会話をできる新しい課」
という依頼を実装する。Actio: `c2ae77d1-8795-4fb3-b317-4cf01f224ac2`。
名称は「企画調整課」を提案・初期採用する。「ゲーム調整課」より仕様・画面も含めやすく、
「プランナー支援課」より何をする場かが分かる。人間による名称の最終承認・実機評価は未実施。

## 価値・シナリオ

UX-CC-W1/W4、UX-CC-S1/S5 に対応する。失うと困る状態は、プランナーが遊びの狙いを伝え、
変更の違いと次に確認することを理解して決められること。技術用語や Git 操作を依頼の前提にしない。

例: 「Ludellus の敵が強すぎる」→ どの場面で困るかだけ確認 → 「攻撃を避ける余裕を増やす」
「失敗しても立て直しやすくする」の違いを説明 → 決まった範囲を調整 → 試す場面と見てほしい点を返す。
「どうすればよいか」の相談と「この内容で変えて」の実施指示を区別し、同じ指示を再確認し続けない。

## 会話の契約 (CC-PLAN-01)

- 日常語、画面名、操作、遊び心地を使う。専門語が必要なら一言で言い換える。
- 対象、困る場面、望む体験、変えたくない点を文脈から拾い、不足だけ一度に最大二問。
  技術レベルや役職を必須回答にしない。分からない数値は例と推奨案で補助し、仮定を明示する。
- 候補は通常二〜三案。各案の体験差、影響、手間を短く示し、数値は単位と変更前後を添える。
- 判断待ちは「何を決めればよいか」、結果は「変えたこと／確認してほしいこと／残っていること」。
  実装済み、審査中、反映済み、試遊未確認を区別する。
- 実装引継ぎには対象、狙い、合意した変更、変えない範囲、確認場面と期待結果、未決事項を残す。
  技術詳細・根拠は必要時に参照できるよう残すが、利用者の判断に不要なログを会話へ羅列しない。

これは対話指示の供給であり、LLM の回答品質・意図判別を機械的に保証するものではない。

## 所有・再利用・不変条件

| ID | 契約・所有者 |
|---|---|
| CC-PLAN-02 | dialogue-context が `planning-adjustment` フォーマットと初期値を所有。edit、依頼者メモあり、技術相談の事前ヒアリングなし。作成済みの編集内容は上書きしない |
| CC-PLAN-03 | governance が部署と出力設定を所有。`startup_inject=full` を保ち、説明の簡略化で作業規則・承認・対象範囲を弱めない。edit は包括的実行許可ではない |
| CC-PLAN-04 | 訂正・依頼者メモは既存の会社境界で分離 (CC-DLG-INV-01/04)。総務の既定部署、技術相談課、CDGD の既存設定・既存セッションを自動変更しない |

新規の状態機械や DB 列は不要。既存 UseCaseService、DepartmentService、起動コンテキストを使う。
支援境界 dialogue-context / governance が session-coordination の参加・意思疎通を支える。
ソース・テスト所属は既存 membership、参照は両 domain の specRefs に追加する。

本社部署 `planning-adjustment` の初期設定:

- 名称: 企画調整課。ユースケース: 企画調整 (`planning-adjustment`)。既定部署にはしない。
- 起動: provider=codex、project=Ludellus。モデル/effort は既存の provider 既定に従う。
  利用者の明示対象が優先。プロジェクト制限を空にしても既存認可は維持する。
- 出力: status_card=on、intermediate=on (短い進捗を残す)。thinking、session_info_card、cost_report、
  inject_transcript、context_usage、session_end_report は off。startup_inject=full。
- CDGD は管理画面で同フォーマットのユースケースを割り当てて再利用できる。
  課の設定がそのまま稼働中の全セッションへ遡って注入されるとは保証しない。

## 反映・復旧

通常はフォーマット提供版へ更新後、既存 `/v1/use-cases`、`/v1/departments` API で作成する。
今回は再起動せず使えるよう、現行の汎用 `chores` 形式に**同じ初期値を明示した専用ユースケース**を
登録する段階導入を選ぶ。これは編集可能な既存契約の利用で、機能の無言フォールバックではない。
専用フォーマット版の反映後は `format` だけ変更可能。人が編集した pre_data や出力設定を上書きしない。
再起動やテストをこの仕様から許可されたと解釈しない。

作成前に slug と所有会社で検索し、同名があれば内容を比較する。応答喪失時は再取得して照合し、
別 slug で複製しない。ユースケース作成後に部署作成が失敗したら、その ID から再開する。
取り消す場合は新部署を廃止して新規受付を止め、稼働セッションは個別に扱う。
DB 直接更新、総務の既定変更、他の課への自動適用はしない。
