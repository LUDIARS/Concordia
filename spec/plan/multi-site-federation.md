# マルチ拠点連合 (本社/子会社/部署)

## 目的

Concordia を複数の拠点 (PC) で動かし、各 PC にログインしたユーザのローカルセッションを
その拠点の Concordia が持てるようにする。同時に本社が全拠点を一元管理する。

## 用語定義

| 用語 | 定義 | 実体 |
|---|---|---|
| 本社 | 中央 Concordia。既存の稼働インスタンス | Discord Gateway の唯一の保持者 |
| 子会社 | 拠点 PC 上のローカル Concordia | ローカルセッション (Claude Code / Codex 等) を所有 |
| 部署 | Discord サーバ (guild) | 現行の guild 単位設定 (`discord/config.ts` の `DiscordConfigSnapshot`) をそのまま部署設定として扱う |

本ドキュメントで Discord サーバ (guild) を指すときは「部署」と呼ぶ。既存の
`subsidiary` (外部サーバへの出張所 Bot) は本設計とは別概念のまま残し、
リネームも再定義もしない。

> **用語衝突の注意**: [../feature/subsidiary-delegation.md](../feature/subsidiary-delegation.md)
> (status: planned) は「子会社 = 外部 Discord/Slack への出張所 Bot + Sonnet ガード」
> という別の意味で「子会社 (subsidiary)」を使っており、DB schema (`subsidiaries` 系)
> と API (`/v1/subsidiaries`) も既にその名前で実装されている。本設計の「子会社 = 拠点 PC 上の
> ローカル Concordia」とは無関係の概念なので、**実装時は同じ語を再利用しない**。
> 本設計側の識別子には `site` / `federation-peer` 等の別語を用い、
> 本ドキュメントの「子会社」は説明用の呼称に留める。

## 要件

1. 本社が全ての子会社を管理できる (Excubitor のように接続できる)。
2. 本社の設定を子会社へ**透過配布**する (子会社は個別設定を持たず、本社で決めた設定が
   そのまま流れて適用される)。
3. 部署 = Discord guild。部署ごとにどの子会社が担当するかをルーティングする。

## Discord プラットフォーム制約 (設計の根拠)

- **Gateway は同一 shard に 1 セッションのみ**。同一 Bot トークンで複数 PC が素朴に接続
  すると相互にセッションを無効化し合う。複数 PC 常時接続は不成立。
- **guild → shard 割当は式で決定済み** (`(guild_id >> 22) % num_shards`。guild_id の
  snowflake タイムスタンプ部を shard 数で割った剰余で、実装側から選べない)。
  「この部署はこの PC」という shard 分担は制御不能 → シャーディング分担案は不採用。
- **REST API は多拠点同時利用可**。ただしレート制限 (グローバル 50 req/s) は
  トークン全体で共有。
- **Interactions の HTTPS エンドポイント受信**は Application に 1 URL のみ。
  通常メッセージ受信には結局 Gateway が必要 → 単独案としては不成立、将来オプション。

## アーキテクチャ (採用案: 本社 Gateway ハブ + イベント連合)

```
Discord ⇄ (Gateway ×1) 本社 Concordia
                          │  連合リンク (WS, Excubitor federation と同型)
              ┌───────────┼───────────┐
        子会社A Concordia   子会社B ...   子会社C ...
        (拠点PCのローカルセッション群)
```

### 受信 (ingress)

1. 本社が Gateway で全部署 (guild) のイベントを受信する (現行どおり)。
2. 本社は**部署ルーティングテーブル** (`guild_id → 子会社 ID`) を引き、
   該当子会社へ連合リンクでイベントを転送する。
3. 本社自身が担当する部署 (未割当 guild 含む) は現行パスで処理する。
   ルーティング未登録の guild は本社担当が既定。

### 送信 (egress)

子会社の Discord 送信は**本社プロキシ経由**に集約する。

- 理由: (a) Bot トークンを子会社へ配布しない (漏洩面の最小化)、
  (b) レート制限 (トークン共有) の一元管理、(c) 送信監査の一元化。
- 子会社は連合リンク上で egress 要求 (channel/thread への post、reaction 等) を送り、
  本社が現行の egress/webhook-pool 経路で実行して結果を返す。
- **本社は egress 要求の宛先を要求元子会社の担当部署にスコープして検証する**
  (ルーティングテーブルで当該子会社に割り当たっていない guild/channel 宛は拒否 +
  監査ログ)。この検証がないと、1 拠点の連合トークン漏洩がそのまま全部署への
  投稿権限になる。

### 連合リンク

- トランスポート: WebSocket over TLS (`wss`) 固定。子会社 → 本社へ outbound 接続
  (拠点側の NAT/FW を跨がない)。平文 `ws` は拠点間がマシンを跨ぐため不可。
- 認証: 拠点ごとの事前共有トークン + 子会社 ID。本社側で登録制 (Excubitor peer と同様)。
  トークンは既存の secret-box (`src/shared/secret-box.ts`) に置き、比較は定数時間で行う。
  認証失敗はレート制限 + 監査ログ。
- 再接続: 子会社側が指数バックオフで再接続。切断中のイベントは本社が
  子会社別キュー (SQLite) に貯め、再接続時に順序保証つきで再送する。
  **キューは上限 (件数 + TTL) を持ち、超過は最古から破棄して破棄件数をエラー
  チャンネルへ通知する**。無制限に貯めると長時間切断で本社 DB を食い潰す。
- ハートビート: 双方向 ping。本社は子会社の生死を管理画面 (要件1) に反映する。

### 信頼境界 (既存不変条件との整合)

現行 Concordia の `/v1` は **token 無しの loopback 信頼境界**が前提で、
非 loopback bind は起動時に拒否される
(`src/bootstrap/core.ts` の `isLoopbackHost` チェック、
[../feature/trust-boundaries.md](../feature/trust-boundaries.md))。
本設計は拠点をまたぐ inbound 接続を本社に持ち込むため、この不変条件と正面から衝突する。
連合リンクは以下を満たすこと。

- 連合リンクの listener は既存の `/v1` HTTP サーバと**別の面**にする
  (別ポート + 別 origin、既定 OFF の opt-in)。既存サーバをそのまま LAN/WAN へ
  bind して兼用してはならない — token 不要の mutation API 全部が外部到達になる。
- 本社の公開面は逆プロキシ / トンネル (AccessControl と同じ経路) の内側に置き、
  `isLoopbackHost` の拒否は緩めない。
- 連合リンクで受け付ける操作は連合プロトコルで明示的に定義したものだけに限定する。
  子会社からの要求を `/v1` へそのまま透過転送する経路は作らない。
- ingress 転送は Discord メッセージ本文を拠点 PC へ複製する。どの部署の内容が
  どの拠点へ渡るかはルーティングテーブルがそのまま情報フロー境界になるため、
  割当変更は監査ログに残す。

### 設定の透過配布 (要件2)

- 設定の正本は**本社のみ**。子会社はローカル設定ファイル/DB を設定正本として持たない。
- 連合リンク接続時に本社が設定スナップショット (部署設定・テンプレート・ルール) を
  push し、以後は差分更新をイベントとして配信する。
- push する範囲は**当該子会社の担当部署分に絞る**。全部署の設定を全拠点へ配ると、
  拠点 1 台の侵害がそのまま全部署の設定漏洩になる。
- 子会社はスナップショットをメモリ + ローカルキャッシュ (再起動直後のオフライン起動用)
  に保持する。キャッシュはあくまで最終受信値であり、編集不可。

### 本社からの管理 (要件1)

- 本社 WebUI に子会社一覧 (接続状態・保有セッション・担当部署・バージョン) を表示。
- 本社から子会社への操作 (セッション spawn 指示・設定再配布・再起動要求) は
  連合リンク上のコマンドとして送る。Excubitor の remote control と同じ考え方だが、
  プロセス lifecycle は各拠点の Excubitor に委ね、Concordia 連合はセッション協調に限定する。

## 障害モード

| 障害 | 影響 | 緩和 |
|---|---|---|
| 本社停止 | 全拠点の Discord 入出力が停止 (単一障害点)。停止中のイベントは Gateway が受信していないので本社キューにも入らない | 子会社のローカルセッション協調は継続。Discord の resume 窓を超えた分の取りこぼしは復旧後も埋まらない (補填の要否は未決) |
| 子会社切断 | 当該部署の応答が止まる | 本社がキュー保持 + 管理画面/エラーチャンネルへ通知。閾値超過で本社が代理応答 (フォールバック) するかは未決 |
| レート制限枯渇 | 全拠点の送信遅延 | egress を本社プロキシに集約しているため、本社側で優先度制御可能 |
| 長時間切断でキュー溢れ | 当該部署の古いイベントが失われる | 上限到達を検知して最古から破棄 + 破棄件数を通知。本社 DB の膨張は防ぐ |
| 連合トークン漏洩 | 当該拠点になりすまして ingress 受信 / egress 実行が可能 | Bot トークン自体は配布していないため Discord の直接操作はできない。被害範囲は「その拠点へ渡す設定スナップショット + 許可する egress 宛先」に等しいので、どちらも担当部署にスコープしておくことが前提 (上記 egress・設定配布の項)。トークンは拠点ごとに分離し、本社から失効できる |

## 不採用案 (記録)

- **シャーディング分担**: guild→shard が式で決まり部署→拠点の割当を制御できない。
  shard 数変更は全拠点同時再編成になり運用が脆い。
- **拠点ごとに別 Application**: 「同じ Bot」前提に反する。ただし連合層完成後の
  フォールバックとしては移行コスト小 (Gateway 制約が消える)。
- **HTTP Interactions エンドポイント**: 通常メッセージ受信に Gateway が必要で単独不成立。
  コマンド経路の Gateway 依存低減の将来オプションとして保持。
- **アクティブ/スタンバイ**: 同時マルチ拠点にならない。連合層完成までの暫定運用としては可。

## 段階導入

- **Phase 0 — 信頼境界の分離**: 連合 listener を `/v1` と別面に切り出し、
  既定 OFF の opt-in で立てられるようにする。`isLoopbackHost` 拒否は維持したまま
  連合面だけを外部到達可能にできることを確認する (これが未了なら Phase 1 に進まない)。
- **Phase 1 — 連合リンク基盤**: 子会社 ⇄ 本社 WS リンク (登録・認証・ハートビート・
  再接続・キュー)。本社 WebUI に子会社一覧。
- **Phase 2 — 設定透過配布**: スナップショット push + 差分配信 + 子会社ローカルキャッシュ。
- **Phase 3 — 部署ルーティング**: ingress 転送 + egress プロキシ。1 部署を試験的に
  子会社へ割当てて実運用検証。
- **Phase 4 — 管理コマンド**: 本社からの spawn 指示・設定再配布・remote control。

## 未決事項

- 子会社切断中の本社代理応答 (フォールバック) の要否。
- 連合リンクのイベントスキーマ (`ConcordiaEvent` をそのまま流すか、連合専用の
  外部スキーマを切るか)。互換性運用の観点では専用スキーマ + バージョン番号を推奨。
- 子会社側 DB (sessions/chat) と本社 DB の同期範囲 (全量ミラーか、担当部署のみか)。
- 連合面の公開方式 (既存 AccessControl の逆プロキシに相乗りするか、専用トンネルか)
  と TLS 証明書の運用。
- 切断キューの具体的な上限値 (件数 / TTL) と、破棄が起きたときの部署側への表示。
- 本設計の「子会社」に充てる実装上の語 (`site` / `federation-peer` / 他) の確定。
  既存 `subsidiary` 系との衝突を避けるため実装着手前に決める。
