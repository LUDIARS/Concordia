# コンパクションの /clear が引き継ぎ資料ごとコンテキストを消す

- Date: 2026-08-15
- Status: investigating
- Area: control / session compaction (`src/control/compaction.ts`)
- Severity: 高 — 作業中セッションのコンテキストが引き継ぎ無しで失われる (復元不能)

## Summary

ある作業セッションが、
Concordia のコンパクションで `/clear` された結果、**再投入されるはずの引き継ぎ資料を受け取らないまま**
空のコンテキストで再開した。新コンテキストに残っていたのは `/clear` の痕跡と、その後の
stalled-session nudge (`[自動確認] しばらく応答が止まっているようです`) だけで、
作業内容 (実装対象・未決事項・直前の修正) は一切引き継がれていない。

記録済みのチャットイベントと transcript の時刻を照合し、誤作動と確認した。

## Evidence

ローカルで確認した Cc のセッションメッセージ記録、および Claude Code transcript の時刻。時刻は UTC。
セッション ID・メッセージ ID・ローカルパスは、運用上の参照情報のためここには記録しない。

| 時刻 (UTC) | 出来事 | 出所 |
|---|---|---|
| 10:41:36 | セッション開始。会話アプリの起動作業 | セッション開始記録 |
| 11:00:27 | コンパクション第1段を inject: 「まもなく `/clear` します。引き継ぎ資料を書け」 | セッションメッセージ記録 |
| 11:02:10 | セッションが引き継ぎ資料 (ゴール・未決事項) を投稿 | セッションメッセージ記録 |
| 11:02:22 | コンパクション第3段 (再投入) 「投稿した資料に従って続行してください」を inject | セッションメッセージ記録 |
| 11:03:07 | ここで初めて `/clear` が適用され、コンテキストが切り替わる | transcript の時刻と旧 transcript 末尾のキュー操作 |

再投入 (11:02:22) が `/clear` の適用 (11:03:07) より **45 秒早い**。
旧 transcript の最終エントリはアシスタントの長文応答 (11:03:07.057Z) と `queue-operation` (11:03:07.143Z) で、
inject 時点でセッションはターン実行中であり、TUI がキー入力をキューしていたことを示す。

結果、新コンテキストには `/clear` のコマンド記録と stalled-session nudge のみが残り、
引き継ぎ資料は存在しない。

## Regression Context

同じ日の複数セッションでは
第1段・第3段が **2 回ずつ** 記録されており、inject の重複や順序ずれが常態化している兆候がある。
つまり本件は単発事故ではなく、「セッションがターン実行中でもコンパクションを開始する」設計の
帰結として再発しうる。

## Cause

`src/control/compaction.ts` の `runCompaction` は
生成 → 投稿 → `inject(sessionId, "/clear")` + Enter → 固定待ち
(`CONCORDIA_COMPACTION_CLEAR_WAIT_MS`、既定 4000ms) → 再投入、の順で **TUI へキーストロークを流すだけ**で、
`/clear` が実際に適用されたことを確認していない。

セッションがターン実行中だと Claude Code は入力をキューし、ターン終了後にまとめて処理する。
このとき固定待ち 4 秒はターン長 (今回は 45 秒以上) を吸収できず、
再投入が `/clear` 適用前に消費され、続く `/clear` が再投入ごと消し去る。

`makeCompactionIO` の inject は event を emit して記録した時点で `true` を返し、
TUI への配信や `/clear` の適用を確認しないため、この失敗は検出も記録もされない。

## Fix Requirements

1. コンパクション開始前に **セッションが idle であること** を条件にする
   (transcript mtime ベースの idle 判定は `src/control/stalled-session-nudge.ts` に既にある)。
   ターン実行中なら開始せず次周期へ送る。
2. `/clear` の適用を **固定待ちでなく観測で確認**する。provider ごとに実装可能な適用確認を
   `runCompaction` の依存として定義し、それを待ってから再投入する。タイムアウト時は再投入せず失敗として記録する。
3. 適用確認できなかった場合は、再投入を行わなかったこととチャンネルへ投稿済みの引き継ぎ資料の参照先を
   **運用者へ通知**する。現状の handoff は clear 前にチャンネルへ投稿されるため、復旧用の正本は残る。
4. 第1段・第3段の重複 inject を抑止する (同一 session の進行中コンパクションを 1 本に限定)。

## Verification

追加すべき回帰テスト (未実装):

- `compaction.test.ts` に「`/clear` の適用確認が成功するまで再投入しない」ケースを足す。
  既存テストは inject 順序 (`compaction-clear` → `compaction-clear-enter` → reinject) のみを固定しており、
  **適用前に再投入されるこの事故を検出できない**。
- idle でないセッション (transcript が更新中) に対して `runCompaction` が開始しないことのテスト。

## Follow-up

  引き継ぎ資料から読み直す。
