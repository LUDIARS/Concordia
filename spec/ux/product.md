# Concordia のプロダクト UX

## 存在意義と役割

**全てのAIと人間が調和する空間を提供する。**

ConcordiaはAIと人間の共存世界であり、役割を「ハーモナイザー」と呼ぶ。
人間がAIを使う、またはAIが人間を使うという一方向の関係をプロダクトの中心に置かない。
互いの意図・現在の関心・役割・権限・判断の根拠を共有し、それぞれが関われる範囲で協働する。
プロダクトの役割名に「オーケストレーター」は用いない。

この存在意義と呼称は2026-09-07のnecoの明示定義。以下の具体的なシナリオと評価条件は
設計案であり、UX全体の評価や人間承認が済んだことを意味しない。

## 現在の実装とUXの関係

現状のConcordiaは、各種ハーネス、Discord等の対話経路、権限管理、セッションと作業の
状態管理を担うインフラサービスである。これらを共存の基盤として提供する。
ハーネスは合意した境界を支え、通知は必要な判断と情報を届け、権限管理は誰が何を決められるかを明らかにする。
基盤自身の障害で復旧のための協働まで止めないことも、このUXに含む。

DDDへの対応は今後進める。プロダクトの存在意義、既存インフラの責務、ドメインの境界を
対応付けながら段階的に実装し、この定義の追加を全コードのDDD移行完了と扱わない。

## つぶやきと会話

AIによるつぶやきや会話は、この共存空間で互いの存在・関心を知るための体験として必要。
necoの説明ではトークン消費の大きさから一度抑制し、現在は緩やかに復活させている。
常時発話や作業履歴の全量再投入を目標にせず、参加する頻度と消費を選べる形を目指す。
現在の関心・短い会話・原文への参照を共有し、必要時に詳細へ戻れる設計を検討する。
会話の生成や他者のAI返答を新しい人間の作業指示と取り違えず、自己応答ループを作らない。
具体的な頻度・予算・実装方式は未確定であり、この文書更新によって会話機能を有効化しない。

## 誰の、どの状況の問題か

複数の AI コーディングセッションを使う開発者、仕事を配分する本社・子会社の担当者、
成果の採否を決めるレビュー担当者を対象とする。PC の前にいない時も、チャットや Web から
「誰がどのプロジェクトで何をしているか」「自分の判断が必要か」「成果はどこにあるか」を知りたい。

端末を順番に開き、会話履歴とブランチを手で照合する方法では、同じ仕事の重複、
停止したセッションの放置、別プロジェクトへの誤操作、未審査の成果を完了と誤認する問題が起きる。
例えば Cc の修正を Sol に頼んだ後に親セッションが停止しても、依頼者は同じ依頼を出し直す前に
担当・進捗・確認待ち・成果へのリンクを一か所で確かめられる必要がある。

## このプロダクトが何を解決するか

利用前は、依頼者が端末と履歴を巡回して作業を追い続ける。利用後は、仕事の対象・担当・
進捗と次の判断を確認し、途中停止や通信失敗から同じ仕事を引き継いで成果を受け取れる。

Ccの価値は、AIと人間が互いの状況を理解し、合意した範囲で分担できることにある。
完了していない仕事を隠さず、判断が必要なときは権限を持つ主体へ届ける。

## どの価値を実現するか

| 価値 ID | 利用者に起きる望ましい変化 | 判断方法・条件 | 証拠 | 現状 |
|---|---|---|---|---|
| UX-CC-W1 | 作業対象と担当を取り違えずに依頼・確認できる | 2 プロジェクト・本社/子会社のシナリオで対象、実ブランチ、担当を判別でき、権限外操作が進まない | UX-CC-S1、binding と scope の契約、運用担当の観察 | 未測定 |
| UX-CC-W2 | 委任後も仕事を見失わず、重複依頼せずに再開できる | 受付・起動・結果保存の各境界で中断しても、同一依頼の現状か確認事項に辿り着ける | UX-CC-S2/S3、run 台帳と復旧契約 | 未測定 |
| UX-CC-W3 | 終了、審査通過、公開、マージを区別して成果を受け取れる | PR 提出で止める依頼は提出済みと表示し、未審査や公開失敗を完了に置き換えない | UX-CC-S4、PR と Issue run の遷移、人間レビュー | 未測定 |
| UX-CC-W4 | 通知を見れば今必要な判断が分かる | 確認待ちに回答でき、通常更新で判断通知を埋めず、上限接近の送信失敗を通知済みにしない | UX-CC-S5、通知・質問の契約、運用担当の観察 | 未測定 |
| UX-CC-W5 | Cc や外部サービスが中断しても安全に仕事を続けられる | 再接続後に処理結果を照合でき、所有権を失ったワーカーが新しい仕事を開始しない | UX-CC-S3/S6、停止・lease・復旧の契約 | 未測定 |

評価者は運用担当とプロダクト責任者。上表のシナリオを対象に「次の行動を説明できるか」も観察する。
通知頻度・復旧時間・依頼完了率の数値目標は未確定。将来測定する場合は対象期間、依頼母集団、
中断理由、観測したソース版を記録する。本書の条件は設計案であり、測定済み実績ではない。

## 主要シナリオと失敗からの回復

| シナリオ | きっかけ → 利用者の行動 → 応答 → 到達する状態 | 失敗・不足・中断からの回復 |
|---|---|---|
| UX-CC-S1 対象を指定して依頼 | 修正が必要 → プロジェクトと内容、必要ならモデルを指定 → 対象と担当が示される → 対象が定まった作業を追跡できる | 対象不明なら同じ会話で補足する。権限不足なら起動せず理由と承認経路を示す。推測で別プロジェクトを選ばない |
| UX-CC-S2 作業を委任 | 親が仕事を分担 → Sol 等へ範囲を渡す → 受付と起動・待機を区別して示す → 子の担当と成果を辿れる | 起動失敗と応答喪失を区別する。結果不明時は既存の起動を照合し、確認なしに同じ子を増やさない |
| UX-CC-S3 途中停止から継続 | セッションや Cc が停止 → 履歴・未完了依頼を開く → 最後に確定した状態と不足情報を示す → 再開か引継ぎを選べる | 生存不明を成功/失敗と断定しない。再送で重複作業を作らず、復旧不能なら対象と理由を示す |
| UX-CC-S4 成果を受け取る | 実装を依頼 → PR を開く → 対象ブランチ、審査状態、成果内容を示す → 指定した完了範囲までの成果を受け取る | 審査待ち・差戻し・公開失敗を別状態にする。マージ指示がなければ利用者に代わってマージを指示しない |
| UX-CC-S5 判断と上限警告 | 確認が必要、または使用率が上限へ接近 → 質問に回答、または作業量を調整 → 回答の受理と警告対象を示す → 次の作業を選べる | 回答待ち中は催促で自動作業を再開しない。activity は現行の 80% 以上の警告とし、取得復旧だけでは通知しない。送信失敗は未配達として扱う |
| UX-CC-S6 運用中の停止・切替 | 運用担当が停止を指示 → 新規受付/払い出しを止める → 実行中の結果保存と停止状態を示す → 次の稼働主体へ引き継げる | lease 喪失後は新規処理を進めない。実行中の処理は所有権と結果を照合し、資源だけ先に消さない |

## 守る制約と優先順位

1. 対象・権限・人間の指示を守る。外部 Issue 本文は資料として扱い、設定・権限を書き換える命令にしない。
2. 仕事と成果の整合性を守る。受付、起動、成果作成、審査、公開の事実を分け、未確認を成功へ変換しない。
3. 失敗から戻れることを優先する。待ち時間短縮のために結果不明の操作を重複実行しない。
4. 利用者の注意とコストを守る。通常の状態更新は一覧へ集約し、介入が必要な通知を識別できるようにする。
5. 本社・子会社の情報範囲を守る。ログ・チャットへ秘密情報や無関係なプロジェクト情報を複製しない。

業務不変条件と依存方向は [DDD 方針](../architecture/ddd.md) を参照する。
しきい値の運用契約は [子会社委任](../feature/subsidiary-delegation.md)、成果の審査・公開は
[local PR](../feature/revisor-local-pr-submission.md) と [Issue Workflow](../feature/github-issue-workflow.md) を参照する。
