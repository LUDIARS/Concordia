# セッション協調の UX

## 誰の、どの状況の問題か

複数セッションを並行運用する開発者と運用担当が、端末を開き直さずに担当・対象・進捗・
確認待ちを把握したい場面を扱う。プロセスが生きているだけでは、依頼が進んでいるのか、
人間の回答待ちなのか、どのブランチを実際に編集しているのか分からない。

例：同じ workspace から Cc と別プロジェクトのセッションを起動しても、作業先が決まった後は
各プロジェクトの実 checkout が表示され、別セッションの停止・終了を取り違えない。

## このプロダクトが何を解決するか

[プロダクト UX](product.md) の UX-CC-W1/W4/W5 に貢献する。担当と作業対象、最後の確定状態、
次に必要な人間の行動を結び、対象を再調査し続ける負担を減らす。

本ドメインをコアとする分類案の理由は、複数 AI の協調と中断時の継続が Cc 固有の価値だからである。
永続化方式、チャット SDK、プロセス起動方式は支援機構であり、その実装詳細を価値と同一視しない。
委託 run の実行責任と PR の審査判定は所有しない。

## どの価値を実現するか

| 価値 ID | 利用者に起きる望ましい変化 | 判断方法・条件 | 証拠 | 現状 |
|---|---|---|---|---|
| UX-CC-SC-W1 | 別プロジェクトや古いブランチへ誤操作しない | 同一 workspace の異なる作業を対象・担当で識別でき、古い報告で明示 binding が戻らない | UX-CC-S1、CC-INV-01 | 未測定 |
| UX-CC-SC-W2 | 停止と確認待ちを見分けて仕事を引き継げる | 最後の状態と未完了内容を確認でき、回答待ちに自動継続を始めない | UX-CC-S3/S5、CC-INV-04/08 | 未測定 |
| UX-CC-SC-W3 | 必要な通知を見落とさず、同じ状況を何度も確認しなくて済む | 配達失敗を成功扱いにせず、警告の失敗で状態投稿を重複作成しない | UX-CC-S5、CC-INV-06 | 未測定 |

評価は運用担当が PC と遠隔チャットの双方で行う。コードの状態遷移の合格に加えて、
対象の判別と次の操作が文面から理解できるかを観察する。測定済みの利用実績はまだない。

## 主要シナリオと失敗からの回復

- **SC-S1 登録と対象の確定**：セッション起動 → プロジェクトと実 branch の登録 → 他担当と区別された表示 → 同じ対象の作業を追跡する。対象不明は確認を求め、workspace 名で対象確定を代用しない。
- **SC-S2 停止・引継ぎ**：進捗が止まる → 履歴を確認 → 生存状況と最後の確定内容を提示 → 再開または引継ぎへ進む。heartbeat の欠落だけで仕事を完了にしない。
- **SC-S3 人間の判断**：確認事項が出る → 依頼者が同じ会話で回答 → 対象の質問に回答を適用 → 作業再開または待機継続。別セッションの回答や自動巡回を承認として使わない。
- **SC-S4 通知先停止**：警告の送信が失敗 → 配達を未完了として保持 → 同じ対象の通知を再試行 → 警告を受け取る。cost 状態表示の更新と activity 警告を別の結果として扱う。

## 守る制約と優先順位

対象・権限の正確さ、状態の証拠、復旧可能性、表示速度の順に優先する。
人間の待機指示と回答待ちは守り、催促によって作業範囲を拡張しない。
チャットの停止を理由に session の台帳を書き換えず、秘密情報を通知本文に含めない。

## 対応関係・非目標・未決事項

| 価値 | シナリオ | 不変条件 | 対応する既存仕様 |
|---|---|---|---|
| UX-CC-SC-W1 | SC-S1 | CC-INV-01/02 | [spawn target](../feature/delegation-spawn-target-validation.md) |
| UX-CC-SC-W2 | SC-S2/SC-S3 | CC-INV-04/08 | [shutdown](../feature/session-shutdown.md)、[自律継続](../feature/autonomous-work-continuation.md) |
| UX-CC-SC-W3 | SC-S4 | CC-INV-06 | [message layer](../feature/session-message-layer.md)、[子会社委任](../feature/subsidiary-delegation.md) |

不変条件 ID の定義は [DDD 方針](../architecture/ddd.md)。各シナリオの人間レビューは未実施。
session-lifecycle は行の更新、autonomous-continuation は継続提案、chat-platforms は配達を担う
既存の下位責務として連携し、本 UX を理由に所有ファイルを一括移動しない。

非目標はチャット製品自体の可用性保証と、AI の思考内容の推測。状態の鮮度目標や通知文面の
受け入れは、運用担当が観測しプロダクト責任者が判断する。本書は未承認の draft。
